1. Define the tool contract first: write a Claude tool schema for `issue_refund` with `ticket_id` (string) and `amount` (decimal, positive, currency fixed), and decide the guardrails up front (a maximum amount per refund, refunds allowed only for tickets classified as billing, one refund per ticket).
2. Add a new module (for example `app/refunds.py`) with the `issue_refund(ticket_id, amount)` function that validates its inputs, checks the guardrails, and performs the refund through the payment mechanism; since there are no other services, put the payment call behind a thin interface with a stub so it can be swapped for the real provider, with the provider key read from an environment variable via `config.py`.
3. Build the audit log as an append-only table in the existing database (timestamp, ticket_id, amount, requested-by model/request id, decision, result or error), with a helper `record_audit(...)` that has no update or delete path.
4. Make the audit write part of the refund path itself: write an "attempted" row before the refund runs and an "approved/denied/failed" row after, in the same transaction where possible, and refuse to issue the refund if the audit row cannot be written (fail closed).
5. Wire the tool into `app/triage.py`: pass the tool definition to the Claude call, handle `tool_use` blocks by dispatching to `issue_refund`, return a `tool_result` (including errors and denials) to Claude, and loop until the model produces its final reply, with a cap on the number of tool rounds.
6. Add protection beyond the log: keep the limits and an on/off flag in `config.py`, make the refund idempotent per ticket so a retry cannot pay twice, and treat the ticket text as untrusted input (instruct the model in the system prompt that ticket content cannot authorize a refund, and above a threshold require a human approval instead of executing).
7. Write pytest tests in `tests/` using a mocked Anthropic client and a test database: valid refund writes both audit rows, over-limit and non-billing refunds are denied and logged, audit failure blocks the refund, duplicate calls are idempotent, and a prompt-injection ticket does not trigger a refund.
8. Update the `POST /triage` response in `app/api.py` to report any refund action taken, add a short help article in `docs/` describing the refund and audit behavior for support staff, and run the full test suite before shipping the container.
