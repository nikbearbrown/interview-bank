1. Define the agent's tool set as Anthropic SDK tool schemas in app/triage.py: classify_ticket(category: billing|bug|how-to), search_docs(query) over the 40 markdown articles in docs/, draft_reply(text), save_reply(ticket_id, text), and escalate(reason). Keep each tool narrow with strict input schemas, and keep save_reply as the only write.
2. Write a short system prompt that tells Claude to work one action at a time: look at the ticket, pick the single best next tool call, read the result, and then decide again. It should include no planning or outline phase, only the instruction to act, observe, and continue, plus a rule to finish by calling save_reply exactly once.
3. Implement the loop with the SDK's Messages API: send the ticket plus tools, execute each tool_use block in Python, append the tool_result to the conversation, and call Claude again until it returns end_turn or a stop condition. Add a hard cap on steps (for example 8) and a token and time budget so a stuck agent cannot loop forever.
4. Guard the write: make save_reply idempotent per ticket_id, validate that the reply is non-empty and the category is one of the three allowed values, and refuse a second save in the same run. If the step cap is hit without a save, fall back to escalate instead of writing a partial reply.
5. Load docs lazily: search_docs returns only short matching snippets with filenames, and a read_doc(name) tool fetches a single article on demand, so the 40 articles (about 24,000 words) never all enter the context. Enable prompt caching on the system prompt and tool definitions to cut cost across steps.
6. Wire it into POST /triage in app/api.py: validate the request, run the agent loop, return the category, reply, and a trace of the steps taken, and map failures such as API errors, timeouts, and step-cap hits to clear HTTP responses. Read the API key and settings (model name, step cap) from config.py and environment variables.
7. Write pytest tests in tests/ with a stubbed Claude client that returns scripted tool_use sequences: a normal billing ticket, a how-to ticket that needs a doc lookup, a malformed tool call, a step-cap overrun, and a duplicate save attempt. Assert that save_reply is called exactly once with the right ticket_id on the success paths and never on the failure paths.
8. Run a small manual evaluation on a handful of sample tickets with the real model, reviewing the traces for wasted steps, wrong categories, or replies that ignore the docs. Tune the system prompt and tool descriptions accordingly, then rebuild the single container and check the endpoint end to end.
