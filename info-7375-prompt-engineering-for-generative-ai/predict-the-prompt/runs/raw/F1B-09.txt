1. Define the tool schema for `issue_refund(ticket_id, amount)` in `app/triage.py` (name, description, input_schema with ticket_id as string/int and amount as a positive number with a sane maximum), and pass it in the `tools` list of the Claude call alongside the existing classify/draft flow.
2. Never let the model's tool call execute the refund directly. Add a handler in `app/triage.py` that, when Claude returns a `tool_use` block for `issue_refund`, validates the arguments (ticket exists, amount > 0, amount <= the ticket's billed total and a configured cap from `config.py`) and then stops, creating a pending approval record instead of refunding.
3. Add an approval store: a new `refund_approvals` table (id, ticket_id, amount, status pending/approved/rejected, requested_at, decided_by, decided_at) with helper functions next to `save_reply`, so the gate has durable state that survives restarts of the single container.
4. Add the approval gate endpoints in `app/api.py`: `GET /refunds/pending` and `POST /refunds/{id}/approve` / `/reject`, protected by a human-reviewer credential (an API key or token read from an environment variable via `config.py`, compared in constant time). Only the approve endpoint is allowed to call the real refund function.
5. Implement the actual refund execution as a separate function (`execute_refund`) that is called only from the approve endpoint, re-checks that the status is `pending` and the amount still validates, is idempotent (a double approve cannot refund twice), and writes an audit log entry of who approved what.
6. Return the tool_result to Claude as "refund pending human approval" so the drafted reply tells the customer a refund is being reviewed rather than claiming it was issued, and update the system prompt to say the tool only requests a refund and that the model must not promise one.
7. Add settings to `config.py` (refund cap, approval token, on/off feature flag defaulting to off) so the tool is only offered to Claude when enabled, with no secrets in code.
8. Write pytest tests in `tests/` with a mocked Anthropic client: tool call creates a pending record and does not refund, invalid or over-cap amounts are rejected, approve executes exactly once, reject and unauthenticated requests do nothing, and the reply text never claims an unapproved refund; then run the suite.
