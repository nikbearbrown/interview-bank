1. Define the agent's contract before writing anything: input is a ticket (id and text), output is a structured result with category (billing / bug / how-to), a drafted reply, and a recorded plan. The only side effect is save_reply(ticket_id, text), which must happen last and only after the plan has been checked.
2. Add a planning stage in app/triage.py that makes a first Claude call (Anthropic Python SDK) which returns a short structured plan, as JSON via a tool schema, and does not act. The plan lists the classification, which of the 40 docs/ articles are relevant, what the reply must contain, and whether anything is too uncertain or sensitive to auto-save.
3. Build a small docs lookup for the planner and the drafter: load the 40 markdown help articles at startup, index them by title and keywords, and give the planner a compact index (titles plus one-line summaries) so it can pick the few articles to cite without stuffing all 24,000 words into the prompt.
4. Add a plan validation step in plain Python between planning and acting. Check the schema, that the category is one of the three allowed values, that the chosen docs exist, and that the step list contains no unsupported action. If the check fails, retry the planner once with the error message, then fall back to a "needs human review" outcome without writing to the database.
5. Add the execution stage: a second Claude call that receives the ticket, the approved plan, and only the selected articles, then drafts the reply. Pass the plan as the instruction, so the drafter follows it instead of improvising a new approach.
6. Gate the write. Run save_reply only when the plan said "safe to auto-save" and the draft passes simple checks (non-empty, within a length limit, and no content outside the cited articles). Otherwise store nothing and return the plan and draft marked for review, so the single irreversible action is never taken on a bad plan.
7. Wire it into POST /triage in app/api.py: return the category, the plan, the reply, and a status field (saved or needs_review). Put the model name, token limits, retry count, and the API key (read from an environment variable) in config.py, and log each plan and outcome per ticket id.
8. Write pytest tests in tests/ with the Claude client mocked: a normal billing ticket saves exactly once, a malformed plan triggers a retry and then needs_review with no save_reply call, an unknown category never writes, and a plan that cites a missing doc is rejected. Add one small set of real-API example tickets, run manually, to check plan quality.
