1. Define the tool contract first: an `issue_refund(ticket_id, amount)` JSON-schema tool definition for the Anthropic SDK, with a clear description (when to use it, that amount is in a stated currency unit and must be positive) and a strict input schema. Decide the semantics up front: refunds are only for tickets classified as billing, and the tool is an action the model requests, not one it executes unchecked.
2. Add a refunds module (for example `app/refunds.py`) with the function that performs the refund and records it in the database, using the same persistence pattern as `save_reply`. Make it idempotent per ticket so a retried call cannot refund twice, and log every attempt (allowed or blocked) with ticket id, amount, and outcome.
3. Implement the rate limit in code, not in the prompt: a per-ticket cap (one refund per ticket) plus a global sliding-window cap (N refunds per minute/hour) and a maximum amount per refund, with limits read from `config.py` and environment variables. Since the service is one container with no other services, back the counters with the existing database (or an in-process lock-protected store with the database as the source of truth) so limits survive restarts.
4. Wire the tool into `app/triage.py`: pass the tool definition to the Claude call, and add a tool-use loop that, when Claude returns a `tool_use` block, validates the arguments (ticket exists, amount positive and within limits), calls the rate-limited refund function, and returns a `tool_result` to Claude. When the limit is hit, return a clear error result (not an exception) so Claude can draft a reply telling the customer a human will follow up, and cap the loop at a few iterations.
5. Keep the existing flow intact: classification still happens first, `issue_refund` is offered only for billing tickets, and `save_reply` still stores the final drafted reply. Update the system prompt to say the refund tool should be used only when the ticket clearly justifies it and that tool results are authoritative.
6. Surface the outcome in `app/api.py`: extend the `POST /triage` response to include whether a refund was issued, its amount, or that it was blocked by the rate limit, and return a sensible status when the limiter blocks a request. Add the new limit settings to `config.py` with safe defaults (low caps).
7. Write pytest tests with the Anthropic client mocked: tool schema validity, a successful refund, rejection of invalid or oversized amounts, the per-ticket and global rate limits blocking correctly (including window reset), idempotency on retry, and the tool-use loop feeding a limit error back to Claude. Include a test that non-billing tickets never receive the tool.
8. Document and roll out safely: add a short help doc under `docs/` describing the refund behavior and limits, and ship with a conservative default limit and a dry-run setting (log what would be refunded without writing) so the behavior can be observed in the single container before real refunds are enabled.
