1. Define the agent's contract first: a ticket comes in, the agent produces a structured plan (category, proposed routing queue, proposed reply or action, and the one risky step, `save_reply`), and nothing with side effects runs until a human approves that plan. Write this down as the single rule the whole design must satisfy.
2. Add a planning pass in `app/triage.py` that calls Claude with the ticket text and asks for a JSON plan only (classification billing/bug/how-to, routing decision, ordered steps, confidence, and which steps write to the database). Validate the output against a Pydantic model and retry once on a malformed plan, so a bad plan can never reach the approval stage.
3. Keep planning strictly read-only: the planner may look up relevant help articles from `docs/` (a simple keyword or section lookup is enough for 40 articles) but cannot call `save_reply` or any write. Enforce this in code by giving the planning step no write function, not just by telling the model not to write.
4. Persist the pending plan with a plan ID and status (pending, approved, rejected, edited, expired) and expose it through new FastAPI routes in `app/api.py`: `POST /triage` now returns the plan and its ID instead of acting, plus `GET /plans/{id}` and `POST /plans/{id}/decision` for a human reviewer to approve, reject, or edit. Protect the decision route with an auth token read from an environment variable via `config.py`.
5. Build the execution step so it runs only for an approved plan: it re-reads the stored (possibly human-edited) plan, checks the status is approved and not already executed, then calls Claude to draft the reply and calls `save_reply(ticket_id, text)`. Make it idempotent so a repeated approval cannot write twice, and refuse to run if the ticket content changed since planning.
6. Decide the approval policy explicitly: always require a human for any plan that writes, and route low-confidence or ambiguous classifications to a human with a note on why, rather than guessing. Record who approved, when, and what they changed, so the decision is auditable.
7. Add pytest tests in `tests/` with the Claude client mocked: plans validate, no write happens before approval, rejected plans never write, edited plans execute as edited, double approval writes once, and malformed model output is retried then surfaced as an error. Add a small set of recorded sample tickets per category to check classification and routing.
8. Run the full test suite, then try the flow end to end locally with a few real tickets, confirming the plan matches the reply that is eventually saved. Update the relevant `docs/` or README notes on the new approve-before-act flow and keep deployment as the same single container.
