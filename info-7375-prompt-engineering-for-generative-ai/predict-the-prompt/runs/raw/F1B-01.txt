1. Define the tool schema for `issue_refund(ticket_id, amount)` in `app/triage.py` (name, description, JSON input schema with ticket_id as a string and amount as a positive number) and pass it in the `tools` list of the Claude call. State in the system prompt that the model may only request a refund, never assume one was done, and that refunds apply only to billing tickets.
2. Add a tool-use loop around the Claude call: when the response has `stop_reason == "tool_use"`, do not execute the refund directly. Route the `tool_use` block to the approval gate, then return a `tool_result` block to Claude (matching `tool_use_id`) saying "pending approval", "approved and issued", or "denied" so it can finish drafting the reply.
3. Build the approval gate as a separate module (e.g. `app/approvals.py`) that stores each proposed refund as a pending record in the existing database (ticket_id, amount, requested_at, status) and never calls the refund backend itself. A human approves or denies through a new authenticated FastAPI endpoint in `app/api.py` (e.g. `POST /refunds/{id}/approve`), and only that endpoint triggers the actual refund.
4. Add server-side validation that does not trust the model: confirm the ticket exists and was classified as billing, the amount is positive and no greater than the ticket's charge, and it is under a configured maximum and not a duplicate refund for the same ticket. Reject invalid calls before they reach the queue, and return the reason to Claude as an error `tool_result`.
5. Put the new settings in `config.py` (refund max amount, auto-approve threshold if any, approver credential or API key read from environment variables) and keep secrets out of code. Make the actual refund execution idempotent, keyed by ticket_id, and write an audit log of who approved what and when.
6. Make the model's reply honest about state: have `save_reply` store the draft with a refund status (none, pending, approved, denied) so the customer never sees "your refund was issued" before approval, and update the reply once the human decides.
7. Add pytest tests in `tests/` with the Anthropic client mocked: a refund tool call creates a pending record and no refund is issued, approval issues it exactly once, denial does not, invalid amounts and non-billing tickets are rejected, and the approve endpoint refuses unauthenticated requests. Include a test that a repeated approval does not double-refund.
8. Update one of the docs articles and the README or API docs to describe the new endpoint and the human-approval step, then run the full pytest suite and a manual end-to-end test in a staging container with a test refund before deploying the single container.
