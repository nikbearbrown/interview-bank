1. Define the routing contract first: a fixed set of queues (billing, bug, how-to, plus an "unclear/escalate to human" queue) and a structured output schema (category, confidence, chosen queue, rationale, flags such as urgent or contains-PII). Document it in config.py so triage and tests share one source of truth.
2. Add a planning step in app/triage.py that runs before any action: call Claude with the ticket and ask it to return a short structured plan (what the ticket is about, which docs/articles might be needed, which actions it intends to take and in what order). Validate the plan against the schema and reject or retry malformed plans; take no side effects at this stage.
3. Add a plan-checking gate in plain Python between planning and acting: verify every planned action is on an allowlist (classify, look up docs, draft reply, save_reply), that save_reply targets the given ticket_id only, and that low-confidence or sensitive tickets are routed to the human queue instead of auto-replying.
4. Implement the execution step that follows the approved plan one action at a time: classify and route with Claude, retrieve only the relevant docs/ articles (keyword or simple embedding match over the 40 markdown files, loaded once at startup) to ground the draft, then draft the reply with Claude using those excerpts.
5. Make the write safe: call save_reply(ticket_id, text) only after the draft passes a final check (non-empty, references no invented policy, within length limit), make it idempotent per ticket_id so retries cannot duplicate replies, and log the plan and every executed action alongside the result.
6. Handle failures explicitly: set timeouts and bounded retries on Anthropic SDK calls, fall back to the human queue on API errors or invalid plans, and never expose the API key (read from environment variables via config.py) in logs or responses.
7. Update POST /triage in app/api.py to return the plan, the routing decision, and the saved-reply status, with request validation and clear error codes, keeping the service as a single container.
8. Write pytest tests in tests/ using a stubbed Claude client: plan-before-act ordering (no save_reply before an approved plan), allowlist rejection, low-confidence escalation, idempotent saves, malformed-plan retry, and a few representative tickets per category; run the suite and a manual end-to-end check on sample tickets before shipping.
