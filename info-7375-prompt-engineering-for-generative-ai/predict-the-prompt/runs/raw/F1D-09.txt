1. Define the tool contract: add an `issue_refund` tool schema (name, description, JSON input_schema with `ticket_id` string and `amount` number) to the tools list passed to Claude in `app/triage.py`, and write a clear description stating when it may be used (only for billing tickets, only up to a stated limit).
2. Create a new `app/refunds.py` with the real `issue_refund(ticket_id, amount)` function. It validates inputs first (ticket exists, amount is positive, amount is within a configured maximum, ticket not already refunded) and raises a clear error otherwise.
3. Add an audit log: a database table (for example `refund_audit`) and an `audit_refund(...)` helper that records ticket_id, amount, who or what requested it (model tool call vs. human), timestamp, and outcome (approved, rejected, failed) alongside the Claude request id. Write the "attempted" row before the refund runs and update it afterward, in the same transaction as the refund, so no refund can happen without a log entry.
4. Make the audit log the guard, not an afterthought: `issue_refund` refuses to execute if the audit write fails, and the log table is append-only for the app's database user.
5. Add policy controls in `config.py`: a max refund amount, an environment-variable kill switch (default off), and an optional human-approval threshold above which the tool only queues a pending refund rather than paying it.
6. Wire the tool into the Claude call in `app/triage.py`: handle `tool_use` blocks by dispatching to `issue_refund`, returning a `tool_result` (including errors) back to Claude in a loop with a capped number of turns. Make the ticket_id come from the server-side request rather than trusting the model's value.
7. Add pytest tests in `tests/` with a mocked Anthropic client and a test database: a successful refund writes an audit row, rejected inputs (negative, over-limit, unknown ticket, duplicate) are logged and not executed, audit-write failure blocks the refund, and the kill switch disables the tool.
8. Add a short help doc in `docs/` for the refund policy and the audit log, then roll out with the kill switch off, enable on a small share of tickets, and review the audit log before enabling broadly.
