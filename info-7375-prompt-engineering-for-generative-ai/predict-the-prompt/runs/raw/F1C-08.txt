1. Decide where the tool lives: add a new module `app/refunds.py` holding `issue_refund(ticket_id, amount)`, a refund-limiter, and the tool's JSON schema for Claude, so refund logic stays separate from classification and reply drafting in `app/triage.py`.
2. Define the tool contract: validate that `ticket_id` exists and `amount` is a positive number within a configured per-refund maximum, then perform the refund through a single database write and return a structured result (success, or a clear error string) that Claude can read.
3. Implement the rate limit in code, not in the prompt: a sliding-window counter (per ticket and global, e.g. N refunds per hour and a daily dollar cap) persisted in the existing database so it survives restarts and works across container workers; reject over-limit calls with a "rate limit exceeded, escalate to a human" result instead of raising.
4. Add settings to `config.py` (max refund amount, per-ticket and global limits, window length, and an on/off flag), read from environment variables with safe defaults, so limits can be tuned without a code change.
5. Wire the tool into `app/triage.py`: pass the tool definition to the Claude call, run a tool-use loop that executes `issue_refund` when Claude requests it and feeds the result back, cap the number of loop turns, and update the system prompt to say refunds are only for clearly justified billing tickets and that a limit-exceeded result means hand off to a human.
6. Make the write safe: make `issue_refund` idempotent (key on ticket_id plus amount, so a retried call cannot refund twice), log every attempt with its outcome, and keep the limiter check and refund write in one transaction so concurrent requests cannot slip past the limit.
7. Write pytest tests in `tests/` with the Claude client mocked: valid refund succeeds, invalid ticket or amount is rejected, the limit blocks the (N+1)th call, the window resets, duplicate calls do not double-refund, and the tool loop handles a limit error gracefully; also test the `POST /triage` path end to end.
8. Update the relevant help article or an internal note in `docs/` to describe refund behavior and limits, then run the test suite and do a manual check with a sample billing ticket before deploying the single container.
