1. Define the agent's contract: input is a ticket (text plus ticket_id), and the output is a structured plan (list of proposed actions: classification, which docs to consult, draft reply, whether save_reply will be called) that is produced before any action runs. Write this plan schema as a Pydantic model so it can be validated and shown to a reviewer.
2. Split `app/triage.py` into two phases: a read-only planning phase and a separate execution phase. The planning phase may call Claude to classify the ticket (billing / bug / how-to) and to choose which of the 40 `docs/` articles are relevant, but it must not call `save_reply` or any other write.
3. Implement the planner with the Anthropic SDK, using a system prompt that requires Claude to return the plan as structured JSON (via tool use or a forced schema), including its reasoning, confidence, and the exact reply it intends to save. Retrieve only the relevant docs (simple keyword or title matching) rather than stuffing all 40 articles into context.
4. Add the approval gate: persist each pending plan (ticket_id, plan, status=pending, plan hash) in the existing database, and make `POST /triage` return the plan with a plan_id instead of executing it. Add `POST /triage/{plan_id}/approve` (and a reject/edit variant) that records the reviewer's identity and decision, with auth from environment-based secrets in `config.py`.
5. Make execution strictly conditional on approval: the execute phase loads the approved plan, verifies its hash is unchanged and status is approved, then runs the steps and calls `save_reply(ticket_id, text)` once. Make it idempotent so a repeated approve call or retry cannot write twice, and expire stale plans after a configurable time.
6. Handle failure and edge cases: reject malformed or schema-invalid plans and retry the planning call a limited number of times, escalate low-confidence or ambiguous tickets to a human with no draft saved, and never let ticket text override the system instructions (treat ticket content as untrusted data).
7. Write pytest tests with the Claude client mocked: the plan is generated without any DB write, `save_reply` is not called before approval, rejection saves nothing, approval saves exactly once, tampered or expired plans are refused, and the API endpoints return the right status codes. Add a few real-ticket fixtures for each category as a regression set.
8. Update `config.py` with settings (model name, approval timeout, confidence threshold), add logging of every plan and decision for audit, document the new flow in `docs/`, and confirm the single container still runs with no new services.
