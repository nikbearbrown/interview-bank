1. Define the policy first: the maximum amount the agent may refund without a human, which tickets are eligible (billing only), and the rule that every refund needs approval. Put these limits in `config.py` (read from environment variables where they are secrets or deploy-specific).
2. Add a new module with the `issue_refund(ticket_id, amount)` function that calls the payment system. Make it validate ticket_id and amount (positive, within the cap, the ticket is classified billing) and make it idempotent per ticket so a retry cannot refund twice.
3. Build the approval gate as a separate pending-approvals record: when the agent requests a refund, the code only writes a "pending" row (ticket_id, amount, reason, requester) and does not move money. A person approves or rejects it through a protected endpoint, and only an approved row triggers the real refund call.
4. Add the approval endpoints to `app/api.py` (list pending, approve, reject), protected by an auth check using a secret or token from environment variables. Record who approved and when, and make approval single-use so it cannot be replayed.
5. Declare the tool to Claude in `app/triage.py` as a tool definition with a clear description and a JSON input schema, and run the tool-use loop so Claude can request it. The tool handler the loop calls routes to the "request refund" path from step 3, never straight to the payment call, and returns a message such as "refund pending approval" back to Claude.
6. Update the system prompt to say when a refund may be requested, that approval is required and the refund is not guaranteed, and that the draft reply must not promise a refund before approval. Keep `save_reply` as it is, but have the reply reflect the pending status.
7. Add pytest tests with the Claude client mocked: a tool call creates a pending request and moves no money, invalid or over-cap amounts are rejected, an unapproved or already-used request cannot be executed, and approval executes exactly once. Include a test that the model cannot reach the payment call directly.
8. Add audit logging for every request, approval, rejection and execution, update the relevant help article in `docs/` and the deployment notes for the new environment variables, and roll out first in a mode where requests are logged but the payment call is disabled.
