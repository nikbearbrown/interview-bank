1. Define the agent's contract: it first produces a structured plan (ticket id, proposed category of billing / bug / how-to, which of the 40 docs it intends to cite, the draft reply, and the one write it wants to make), and it may not call save_reply until a human has approved that exact plan. Represent the plan as a Pydantic model so it can be validated, stored, and shown to the reviewer.
2. Split app/triage.py into two phases: plan_ticket(ticket) and execute_plan(plan_id). plan_ticket calls Claude through the Anthropic SDK with read-only tools only (classify, search_docs) and returns a plan with no side effects; execute_plan is the only code path that touches save_reply.
3. Add a read-only docs lookup tool for the planning phase that searches the 40 help articles with simple keyword matching, so the plan can name the articles it relied on. Return short excerpts rather than whole articles to keep the context small.
4. Add an approval store inside the existing container (a small table in the current database, with states pending, approved, rejected, edited) that records the plan, a hash of its contents, who decided, and when. Approval is bound to the hash, so any edit to the plan after approval invalidates it.
5. Extend app/api.py: POST /triage now returns a pending plan and its id instead of saving anything; add GET /plans/{id} for the reviewer, and POST /plans/{id}/decision for approve, reject, or edit. Protect the decision endpoint with a reviewer credential read from an environment variable in config.py, and have execute_plan refuse to run unless the stored state is approved and the hash matches.
6. On approval, execute_plan re-checks the plan against the stored hash, calls save_reply exactly once (idempotent on ticket_id and plan id so a retry cannot double-write), and records the outcome. Rejected or edited plans send the reviewer's feedback back to Claude for a revised plan, with a cap on revision rounds.
7. Write pytest tests with the Claude client mocked: no save_reply before approval, rejection and edit paths, a tampered or edited plan failing the hash check, a retried approval not writing twice, and malformed model output being rejected by validation. Add one end-to-end test through the FastAPI test client.
8. Log every plan, decision, and write with the ticket id for audit, and add a short docs note explaining the approve-then-act flow and the reviewer endpoint. Roll out behind a config flag so the old direct-save behavior can be switched off cleanly once the reviewers are using the new flow.
