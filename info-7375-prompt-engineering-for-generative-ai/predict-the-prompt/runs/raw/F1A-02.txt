1. Define the tool schema for `issue_refund(ticket_id, amount)` in `app/triage.py` (name, description, JSON input schema with `ticket_id` as a string and `amount` as a positive number) and pass it in the `tools` list of the Claude call, with a system prompt line saying refunds are only for billing tickets and must be justified by the ticket text.
2. Write the real `issue_refund` implementation in a new module `app/refunds.py` that validates its inputs (ticket exists, is classified billing, amount is positive and not above a configured maximum from `config.py`), performs the refund through whatever payment call the service already uses, and records an audit row in the database.
3. Build the permission gate as ordinary Python outside the model: when Claude returns a `tool_use` block for `issue_refund`, the code does not run it; it saves a pending refund request (ticket_id, amount, model's stated reason) with status "pending" and returns a `tool_result` telling Claude the refund is awaiting human approval.
4. Add the approval path in `app/api.py`: a `POST /refunds/{id}/approve` and `/deny` endpoint, protected by an authenticated approver credential read from an environment variable via `config.py`, which is the only code path that calls `issue_refund` for real, and which re-validates the amount and ticket state at approval time.
5. Add config settings in `config.py` for the refund cap, an optional auto-approve threshold (default 0, so everything needs approval), and the approver secret, all loaded from environment variables and never hard-coded.
6. Update the tool-use loop in `app/triage.py` so it handles `tool_use` stop reasons, returns a `tool_result` for each call (including errors and denials as `is_error` results), caps the number of turns, and still ends by calling `save_reply` with the final drafted reply.
7. Write pytest tests in `tests/` with a mocked Anthropic client covering: a tool call is queued rather than executed, an unapproved or unauthenticated request never triggers a refund, approval executes exactly once (idempotent on repeat), over-cap or non-billing requests are rejected, and the loop terminates and saves a reply.
8. Run the existing and new tests, then try one end-to-end ticket in a staging environment with a test payment account to confirm that the model proposes a refund, the gate holds it, and approval completes it, and note the new environment variables for the container deployment.
