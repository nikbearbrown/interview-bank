1. Define the tool schema for `issue_refund` in `app/triage.py` (or a new `app/tools.py`): a name, a clear description stating it moves real money and must only be used for billing tickets, and an input_schema requiring `ticket_id` (string) and `amount` (number, positive, with a sensible maximum). Pass it in the `tools` list of the Claude call so the model can request a refund.
2. Write the actual refund function `issue_refund(ticket_id, amount)` as a separate, deterministic Python function that validates inputs (ticket exists, is classified billing, amount is positive and not above the original charge or a hard cap from `config.py`) and calls the payment provider, with the provider key read from an environment variable in `config.py`.
3. Build the permission gate in plain Python, outside the model's control: when Claude returns a `tool_use` block for `issue_refund`, do not execute it; instead record a pending refund request (ticket_id, amount, model's stated reason) and return a tool_result telling Claude that the refund is awaiting human approval.
4. Add an approval path: a new FastAPI endpoint in `app/api.py` (e.g. `POST /refunds/{id}/approve`) protected by an auth check (API key or role from environment-configured secrets) that executes the refund only after a human approves it, plus a reject endpoint. Optionally auto-approve below a small configurable threshold in `config.py`, with everything above it requiring a human.
5. Make execution safe: use an idempotency key per ticket and amount so a retried request or repeated tool call cannot refund twice, enforce a status state machine (pending, approved, executed, rejected), and store every request and decision in the database with who approved and when, as an audit log.
6. Update the triage loop to handle the tool-use cycle: send the tool_result back to Claude, let it finish drafting the reply (told the refund is pending, not completed), and call `save_reply` only once. Adjust the system prompt so Claude proposes a refund only when the ticket is clearly billing and justified, and never promises it to the customer before approval.
7. Add pytest tests with the Anthropic client and the payment provider mocked: gate blocks execution without approval, over-cap and non-billing tickets are rejected, double approval is idempotent, unauthorized approval calls fail, and the full flow from ticket to pending to approved to executed works.
8. Roll out safely: ship with the payment provider in sandbox mode and a feature flag in `config.py` defaulting to off, run on a sample of recorded tickets to review the refunds Claude proposes, then enable in production once the approval logs look correct.
