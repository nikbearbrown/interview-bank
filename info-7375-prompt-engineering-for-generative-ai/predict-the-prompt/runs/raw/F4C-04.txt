1. Define the agent's contract: it receives a ticket and first produces a structured plan (classification, intended reply approach, the exact actions it will take including the `save_reply` write), and it may not perform any write until a human has approved that plan.
2. Split `app/triage.py` into two phases: a read-only `plan_ticket(ticket_text)` that calls Claude (using the Anthropic SDK with a JSON-schema or tool-use output) to return the plan, and an `execute_plan(plan)` that performs the approved actions. Only `execute_plan` is allowed to call `save_reply`.
3. Add a plan store (a plans table in the existing database, or a persisted record) holding plan id, ticket id, plan content, status (pending / approved / rejected / edited), reviewer, and timestamps, so approval state survives restarts in the single container.
4. In `app/api.py`, change `POST /triage` to return the plan and a plan id with status pending instead of saving a reply, and add `POST /plans/{id}/approve` and `POST /plans/{id}/reject` endpoints (reject takes a reason; approve may take human edits), protected by authentication whose credentials come from environment variables in `config.py`.
5. Make the approval gate enforced in code, not in the prompt: `execute_plan` loads the stored plan, verifies status is approved and that the plan content is unchanged since approval (hash check), refuses otherwise, and ensures each plan runs at most once so double-clicks or retries don't write twice.
6. Ground the planning prompt in the 40 help articles in `docs/` by retrieving only the relevant few for each ticket rather than loading all of them, and have the plan cite which articles it will rely on so the reviewer can check them.
7. Handle edge cases explicitly: on rejection, feed the human's reason back to Claude for one revised plan; expire stale pending plans; log every plan, decision, and execution for audit; and handle Anthropic API errors and malformed plan output with validation and clear failures.
8. Write pytest tests with Claude mocked: plan generation returns a valid schema, `save_reply` is never called before approval, rejected or tampered plans are refused, re-execution is blocked, and the endpoints enforce auth; then run the suite and do one manual end-to-end check of plan, approve, execute.
