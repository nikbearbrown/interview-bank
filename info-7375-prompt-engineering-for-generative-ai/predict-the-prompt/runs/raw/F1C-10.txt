1. Define the tool contract in `app/tools.py`: an `issue_refund(ticket_id, amount)` function plus its Claude tool schema (name, description, JSON input schema with ticket_id as string and amount as positive number), keeping the real refund call behind one small function so it can be stubbed in tests.
2. Add a rate limiter module (e.g. `app/ratelimit.py`) that enforces a cap on refunds, both a per-ticket limit (one refund per ticket) and a global sliding-window limit (N refunds per hour), with limits read from `config.py` via environment variables. Because the service is one container with no other services, use an in-process store guarded by a lock, and persist refund counts in the existing database so limits survive restarts.
3. Add validation inside `issue_refund` before any side effect: the ticket must exist, the amount must be positive and under a configured maximum, and a refund must not already exist for that ticket. On any failure or rate-limit hit, return a clear error result to Claude rather than raising, so the model can explain the refusal in its reply.
4. Extend `app/triage.py` to pass the tool definition to the Anthropic SDK call and run a tool-use loop: when Claude returns a `tool_use` block, execute `issue_refund`, send back a `tool_result`, and continue until a final text reply, with a hard cap on loop iterations.
5. Update the triage prompt so Claude only considers a refund for billing tickets with a clear, justified cause, never invents amounts, and states in the draft reply what was or was not refunded; consider requiring human approval above a threshold by returning a "pending review" result instead of refunding.
6. Record every refund attempt (ticket_id, amount, outcome, timestamp) in the database for auditing, written in the same transaction as the refund, and add the new settings (limits, max amount, enable flag defaulting to off) to `config.py`.
7. Write pytest tests in `tests/` with a mocked Anthropic client and stubbed refund backend, covering success, over-limit rejection, duplicate refund, invalid amounts, malformed tool input, and the loop iteration cap, and verify `POST /triage` still behaves for non-refund tickets.
8. Roll out safely: ship with the feature flag off, enable in a limited way with low limits, monitor the audit log and rate-limit rejections, then raise limits gradually.
