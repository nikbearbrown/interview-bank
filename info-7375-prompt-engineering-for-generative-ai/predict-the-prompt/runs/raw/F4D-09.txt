1. Define the routing contract in `app/triage.py`: a small set of routes (billing / bug / how-to / escalate-to-human) and a typed result (route, confidence, reply draft, reasoning), so every step has an explicit input and output to check.
2. Build the agent as a bounded loop using the Anthropic SDK's tool-use messages API: Claude gets tools such as `search_docs`, `classify`, `draft_reply`, and `save_reply`, and the loop runs at most a fixed number of turns (e.g. 6) with a token budget, so it cannot run away.
3. Add a "reflection" step after every tool result: before the next action, Claude must write a short structured note (what the result showed, whether it is sufficient or suspicious, what to do next), and the loop stores this note in the message history so later steps can use it.
4. Give `search_docs` a cheap implementation over the 40 help articles (keyword or chunked-embedding lookup loaded once at startup), returning short excerpts with article IDs, so reflection can judge whether the retrieved text actually supports the draft reply.
5. Make the reflection gate decisions: if classification confidence is low or the docs do not support the draft, the agent re-classifies, searches again with a rewritten query, or routes to "escalate"; only a reflected-and-approved draft may call `save_reply`, which is the one database write, done once per ticket and idempotently by ticket_id.
6. Wire it into `POST /triage` in `app/api.py`, returning the route, reply, and a trace of steps and reflections; read the API key and limits (max turns, model name, confidence threshold) from environment-driven `config.py`, with timeouts and retries on SDK calls and graceful fallback to escalate on errors.
7. Write pytest tests with a stubbed Anthropic client that replays scripted tool-use sequences: a clean billing ticket, a case where reflection triggers a re-search, a loop that hits the turn cap, malformed tool output, and a check that `save_reply` is never called twice or before approval.
8. Run a small evaluation on sample tickets with the real model (tracking route accuracy, steps per ticket, and cost/latency versus a single-call baseline), log traces for review, and tune the reflection prompt and thresholds before deploying the single container.
