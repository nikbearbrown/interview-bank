1. Define the agent's contract: ticket text in, a structured plan out (classification of billing/bug/how-to, which of the 40 docs articles it intends to cite, and the draft reply outline), with no side effects until a human approves. Specify this as Pydantic models so every stage has a typed input and output.
2. Add a planning stage in app/triage.py that calls Claude (via the Anthropic SDK, using tool-use or JSON output for a validated schema) to produce the plan only. The planner may use read-only tools such as searching the docs/ articles, but it must not have access to save_reply.
3. Persist the pending plan with a plan_id and status "awaiting_approval" (stored alongside the existing database, since there are no other services), including the ticket text, the plan, and a hash of the plan so edits can be detected.
4. Split the API in app/api.py: POST /triage now returns the plan and plan_id instead of saving anything, and a new POST /triage/{plan_id}/approve (plus a /reject endpoint with optional edits) takes the human's decision. Protect these with authentication read from environment variables in config.py, and record the reviewer's identity.
5. Implement the execution stage so it runs only when the plan is approved and unchanged: it calls Claude to draft the reply following the approved plan, then calls save_reply(ticket_id, text) exactly once, idempotent on plan_id so retries or double-clicks cannot write twice. Rejected or expired plans never reach save_reply.
6. Enforce the approval gate in code, not in the prompt: execution checks the stored status and plan hash, and the executor's tool list excludes anything outside the approved plan's steps. Add timeouts, a retry limit, and clear handling for Claude API errors and schema-validation failures.
7. Write pytest tests with the Anthropic client mocked: plan generated without a DB write, approve leads to exactly one save_reply, reject and unapproved calls never write, tampered plan is refused, and duplicate approval is idempotent. Also add a few prompt-behavior checks for classification on sample tickets.
8. Update docs and config: document the two-step flow, new environment variables, and the review process; log each plan, decision, and write for auditing; then roll out behind a config flag in the single container, starting with all tickets requiring approval.
