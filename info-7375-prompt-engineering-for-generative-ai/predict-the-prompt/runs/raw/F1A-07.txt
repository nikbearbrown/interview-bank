Define the tool schema for `issue_refund(ticket_id, amount)` in `app/triage.py` (or a new `app/tools.py`) as a Claude tool definition with a JSON input schema: `ticket_id` as a string and `amount` as a positive number, plus a currency and a clear description stating it moves money and requires approval.
2. Put the real refund logic in a plain Python function `issue_refund` that is never called directly from model output. Add a hard server-side cap in `config.py` (for example `REFUND_AUTO_LIMIT` and `REFUND_MAX`), read from environment variables, and validate that the ticket exists, is a billing ticket, and the amount is within bounds.
3. Build the permission gate as ordinary Python code outside the model: when Claude returns a `tool_use` block for `issue_refund`, the code does not execute it but records a pending refund request (ticket_id, amount, who or what requested it, timestamp) in the database. Execution happens only after an explicit human approval, or automatically only for amounts under the configured limit.
4. Add an approval path in `app/api.py`: a `GET /refunds/pending` endpoint and a `POST /refunds/{id}/approve` (and `/deny`) endpoint protected by an API key or token from an environment variable, which runs `issue_refund` once and records the approver. Make approval idempotent so a double click cannot refund twice.
5. Update the triage loop to handle `tool_use` and `tool_result` messages: for gated calls, return a tool_result telling Claude the refund is "pending human approval" (never "completed"), so the drafted reply does not promise money that has not been sent. Keep `save_reply` behaviour unchanged for the non-refund path.
6. Adjust the system prompt so Claude only proposes a refund for clear billing cases, explains its reason, and never states in the customer reply that a refund was issued until approved. Expose the tool only when the classification is billing, to limit its reach.
7. Add pytest tests with the Anthropic client mocked: the refund is not executed without approval, over-limit and negative amounts are rejected, approval runs exactly once, unauthenticated approval fails, and a non-billing ticket cannot get the tool. Add an audit-log assertion that every request, approval, and denial is recorded.
8. Document the new tool, the gate, and the new environment variables in `docs/` or the README, and roll out with the gate set to "always require approval" first, loosening the auto-approve threshold only after reviewing real pending requests.
