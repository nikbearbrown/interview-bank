1. Define the refund tool schema for Claude in app/triage.py: `issue_refund` with typed `ticket_id` (string/int) and `amount` (positive number, currency fixed), plus a clear description saying it is only for billing tickets and must be justified in the reply.
2. Create a new module (e.g. app/refunds.py) with the real `issue_refund(ticket_id, amount)` function, and add hard guardrails in code, not in the prompt: validate the ticket exists and was classified as billing, enforce a per-ticket and per-call maximum amount (configurable in config.py), and reject duplicates for the same ticket.
3. Build the audit log as an append-only database table (ticket_id, amount, caller/model request, timestamp, outcome, reason, request id) written through the same database layer as save_reply. Write an "attempted" row before the refund runs and an "approved/denied/failed" row after, so every call is recorded even when it errors or is blocked.
4. Make the audit write mandatory: if the audit row cannot be written, the refund does not execute (fail closed). Wrap the refund and its audit entries in one transaction where possible, and keep no secrets or full customer text in the log.
5. Add a human-approval path for risky refunds: amounts above a configurable threshold are queued as "pending approval" instead of executed, and the tool returns that status to Claude so the draft reply says the refund is under review.
6. Wire the tool into the Claude call in triage.py with the Anthropic SDK tool-use loop: pass the tool definition, detect `tool_use` blocks, run `issue_refund` in our code, return a `tool_result` (including errors), cap the number of loop iterations, and continue until Claude produces the final classification and reply. Take the ticket_id from the server-side request context rather than trusting the model-supplied value.
7. Add pytest tests with the Anthropic client mocked: valid refund writes both audit rows, over-limit and non-billing tickets are denied and logged, audit failure blocks the refund, duplicate refunds are rejected, and prompt-injection text in a ticket cannot trigger a refund beyond the limits.
8. Add a short docs/ article for the refund policy and audit log, expose the limits via environment-driven settings in config.py, and roll out behind a feature flag (default off) so the tool can be enabled in the single container after reviewing initial audit entries.
