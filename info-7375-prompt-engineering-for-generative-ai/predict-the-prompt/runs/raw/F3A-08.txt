1. Define success first: a small set of sample tickets (billing, bug, how-to) paired with the help article(s) that should answer each, so retrieval and reply quality can be measured before and after the change.

3. Implement chunk ranking for a ticket with a simple, dependency-light method first (BM25 keyword scoring over chunks), return the top 3-4 chunks, and put the scoring behind a function so it can be swapped for embeddings later if recall is poor.

Change the drafting call in app/triage.py so the prompt includes the retrieved chunks inside clearly delimited document blocks with their titles, and instruct Claude to answer only from those excerpts, cite the article it used, and say it cannot answer (flagging for a human) when the excerpts do not cover the question.
5. Keep classification (billing / bug / how-to) as a separate call or step, and optionally use the category to filter or boost articles; keep the ticket text clearly separated from the documents so ticket content is treated as data, not instructions.
6. Make the behaviour configurable in config.py (number of chunks, max context size, a model name, a retrieval on/off flag), with the API key still read from environment variables, and handle failures such as zero hits or an API error without calling save_reply with a bad draft.
7. Add pytest tests: chunking and ranking against the sample tickets with known expected articles, prompt-assembly tests, and triage tests that use a stubbed Claude client and a stubbed save_reply so no real API calls or database writes happen; include a no-relevant-article case.
8. Run the sample tickets through old and new behaviour, compare how often replies are grounded in the right article and how often the unanswerable case is escalated, then ship behind the config flag and watch the first real tickets.
