1. Decide the retrieval design: with 40 articles of about 600 words, chunk each article by heading or paragraph (roughly 200 to 300 words) and index the chunks for retrieval. Start with simple keyword retrieval (BM25 via a small Python library) and only add embeddings if keyword recall proves too weak, since this is one container with no other services.
2. Add a new module, for example app/retrieval.py, that loads and chunks everything in docs/ at startup, builds the index in memory, and exposes retrieve(ticket_text, k) returning the top k chunks with their article names. Keep it free of any Claude or database calls so it is easy to test.
3. Change the reply-drafting call in app/triage.py to retrieve for each ticket, using the ticket text plus the predicted category (billing / bug / how-to) as the query. Insert the top 3 to 5 chunks into the prompt inside clearly labelled, delimited document blocks that include the article name.
4. Rewrite the drafter's system prompt so Claude answers only from the supplied articles, cites the article it used, and says it cannot answer and flags the ticket for a human when the articles do not cover the question. Treat the article text and the ticket text as data, not instructions.
5. Handle the failure paths: if retrieval returns nothing above a minimum relevance score, skip drafting from the articles and return a safe escalation reply. Make sure save_reply is called only after the drafted reply has been checked, so an empty or unsupported answer is never written to the database as if it were grounded.
6. Add settings to config.py (docs path, number of chunks, relevance threshold) with sensible defaults, and keep the existing environment-variable handling for the Anthropic API key unchanged.
7. Write pytest tests: unit tests for chunking and retrieval using small fixture articles, a triage test with the Anthropic client mocked that checks the retrieved chunks appear in the prompt, and a test that a no-match ticket escalates and does not save an invented answer. Include a POST /triage test through the FastAPI app.
8. Evaluate on a hand-made set of 15 to 20 realistic tickets with known correct articles, measuring whether the right article is in the top k and whether drafted replies stay faithful to the articles. Tune chunk size, k, and the threshold from the results, then confirm the container still builds and starts with the docs/ folder included.
