1. Define the tool's contract in `app/tools.py`: an `issue_refund(ticket_id, amount)` function plus its Claude tool schema (name, description, JSON input schema with `ticket_id` as string and `amount` as a positive number), keeping the real refund call behind a single function that is easy to mock.
2. Add a rate limiter module (`app/ratelimit.py`) that enforces a per-ticket cap (one refund per ticket) and a global cap (N refunds per time window), storing counters in the existing database so the limit survives restarts and works within the single container.
3. Put hard validation inside `issue_refund` itself, not in the prompt: reject unknown tickets, non-positive amounts, and amounts above a configured maximum, and return a structured error result that Claude can read rather than raising.
4. Add settings to `config.py` (rate-limit window, max refunds per window, max refund amount, an on/off flag defaulting to off), with any payment-provider credentials read from environment variables.
5. Update `app/triage.py` to pass the tool schema to Claude and run a tool-use loop: when Claude requests `issue_refund`, check the rate limit first, execute or return a "rate limit exceeded" tool result, send the result back, and cap the loop at a small number of turns.
6. Update the triage system prompt to tell Claude when refunds are appropriate (billing tickets only), that the tool may refuse, and to mention the refund in the drafted reply only if the tool call succeeded; briefly document refund behavior in a `docs/` article if one covers billing.
7. Write pytest tests in `tests/` with a mocked Claude client and mocked refund backend: the happy path, a rate-limit hit, the per-ticket duplicate, invalid amounts, and a non-billing ticket that never triggers the tool.
8. Log every refund attempt (ticket id, amount, allowed or blocked) for audit, then roll out with the flag off, enable it in staging-like settings first, and verify the limit holds before turning it on in the deployed container.
