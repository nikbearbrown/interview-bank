1. Define `issue_refund(ticket_id, amount)` in a new `app/refunds.py` as the single function that performs the refund, and make it validate inputs (ticket exists, amount is a positive number, amount does not exceed a configured per-refund cap read from `config.py`).
2. Add a `REFUND_APPROVAL_MODE` setting and a `MAX_AUTO_REFUND` limit to `config.py`, defaulting to the safest option (every refund requires explicit human approval), with any payment credentials read from environment variables.
3. Build the permission gate as a separate `authorize_refund(ticket_id, amount)` check that sits between Claude's tool call and `issue_refund`; it records a pending approval request in the database and returns "approved", "denied", or "pending" based on a human decision, so the model can never trigger the refund on its own authority.
4. Declare the tool in the Anthropic SDK `tools` list in `app/triage.py` with a JSON schema (integer or string `ticket_id`, positive number `amount`) and a description that tells Claude to request a refund only for clear billing cases and that a human will review it.
5. Extend the tool-use loop in `app/triage.py` to handle `tool_use` blocks: route each `issue_refund` call through the gate, execute it only on approval, and send back a `tool_result` ("refund issued", "awaiting approval", or "denied: reason") so Claude can finish drafting the reply accordingly.
6. Add an approval endpoint in `app/api.py` (for example `POST /refunds/{request_id}/decision`) protected by an authentication secret from the environment, so a human reviewer can approve or deny pending refunds, and have approval trigger the actual `issue_refund` call exactly once (idempotent on ticket_id and amount).
7. Write audit logging for every request, approval, denial, and execution (ticket_id, amount, who decided, timestamp), and make sure `save_reply` only mentions a refund as done after it has actually been issued.
8. Add pytest tests in `tests/` with the Claude client mocked: refund blocked without approval, blocked above the cap, rejected for invalid amounts, executed once on approval, duplicate approvals ignored, and the denied or pending result correctly reflected in the drafted reply.
