1. Define the tool schema for `issue_refund(ticket_id, amount)` in `app/triage.py` (name, description, JSON input schema with ticket_id as string and amount as a positive number) and pass it in the `tools` list of the Claude call, with a system prompt line saying refunds are only for billing tickets and must be justified by the ticket text.
2. Add a separate `app/refunds.py` holding the real `issue_refund` function and a `check_refund_permission(ticket_id, amount)` gate. The gate checks the ticket is classified as billing, the amount is positive and under a configurable per-refund cap, a daily total cap is not exceeded, and the ticket has not already been refunded.
3. Add the cap values and an `REFUND_AUTO_APPROVE_LIMIT` setting to `config.py`, read from environment variables with safe defaults (refunds disabled or very low unless set), so no secrets or limits are hardcoded.
4. Make the gate sit in application code, not in the prompt: when Claude returns a `tool_use` block for `issue_refund`, the tool-execution loop in `triage.py` calls the gate first and only calls the real function if it passes. Amounts above the auto-approve limit are not executed but recorded as a pending approval row (a new table via the existing database layer) for a human to approve, and a `tool_result` saying "pending human approval" is returned to Claude.
5. Make execution safe: validate the tool inputs again server-side (ticket exists, amount is a decimal with two places), make the refund idempotent on ticket_id so a retried request cannot refund twice, and write an audit record (who, ticket, amount, decision, reason) for every allowed and denied attempt.
6. Update the tool loop to feed each tool result (success, denied, or pending) back to Claude so the drafted reply tells the customer the true outcome, and cap the number of loop iterations. Keep `save_reply` after the loop finishes.
7. Add a small `POST /refunds/{id}/approve` endpoint in `app/api.py`, protected by an admin token from an environment variable, that lets a human release pending refunds through the same execution path.
8. Write pytest tests in `tests/` with the Anthropic client mocked: allowed refund, over-cap refund goes to pending, non-billing ticket denied, duplicate refund blocked, invalid amount rejected, and the gate cannot be bypassed by the model. Run the full test suite before finishing.
