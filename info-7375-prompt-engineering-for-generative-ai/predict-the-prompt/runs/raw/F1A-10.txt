1. Define the tool schema in `app/triage.py` (or a new `app/tools.py`): an `issue_refund` tool with a clear description and an input_schema requiring `ticket_id` (string) and `amount` (number, positive, with a stated currency), passed in the `tools` list of the Claude messages call.
2. Write the refund function itself, with strict validation: the ticket must exist, the amount must be positive and capped by a configurable maximum in `config.py`, and the same ticket cannot be refunded twice (idempotency key based on ticket_id). The refund provider key comes from an environment variable.
3. Build the permission gate as ordinary Python code outside the model: when Claude returns a `tool_use` block for `issue_refund`, the code does not execute it but records a pending refund request (ticket_id, amount, model's reason) and returns a tool_result telling Claude that approval is pending.
4. Add approval endpoints in `app/api.py`, such as `GET /refunds/pending` and `POST /refunds/{id}/approve`, restricted to authorized staff via a token read from the environment. Only an approved request executes the refund, and every approval, denial, and execution is written to an audit log table next to `save_reply`.
5. Add a small auto-approve policy in `config.py`, default off: amounts under a low threshold for billing-classified tickets may skip human approval, and everything else requires it. The gate decides this in code, never by what the model says.
6. Update the triage prompt so Claude only proposes a refund for tickets classified as billing, explains its reasoning in the reply draft, and never tells the customer a refund has been issued until the gate confirms it. Handle the tool-use loop (`stop_reason == "tool_use"`) and cap the number of iterations.
7. Write pytest tests with the Anthropic client mocked: the gate blocks execution without approval, rejects over-limit and duplicate refunds, rejects unauthorized approvers, executes exactly once after approval, and a malformed tool call from the model is handled safely.
8. Run the full test suite, then try the flow end to end against a sandbox refund provider with a test key. Update the docs and deployment environment variables, and roll out with the gate required for every refund first, loosening only after reviewing the audit log.
