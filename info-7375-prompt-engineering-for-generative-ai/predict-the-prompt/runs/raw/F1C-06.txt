1. Define the tool contract first: `issue_refund(ticket_id, amount)` with a JSON input schema (ticket_id string, amount as a positive number in a fixed currency) and a precise description, so Claude knows when to call it and that it moves real money.
2. Add a new module (e.g. `app/refunds.py`) holding the refund function. It validates inputs (ticket exists, amount > 0, amount not above a configured per-refund maximum), performs the refund, and writes an audit record (ticket_id, amount, timestamp, caller) to the database.
3. Implement the rate limit inside that module, not in the prompt: a sliding-window counter stored in the database (the container is a single service, so no new infrastructure), with per-ticket limits (e.g. one refund per ticket) and a global limit (e.g. N refunds per hour and a daily dollar cap). When exceeded, return a structured error such as `{"error": "rate_limited", "retry_after": ...}` instead of raising.
4. Put the limits in `config.py` as settings read from environment variables (max amount, window length, max count, daily cap), with safe defaults, so they can be tuned per deployment without a code change.
5. Wire the tool into `app/triage.py`: add the tool definition to the Claude call, and add a tool-use loop that executes `issue_refund` when Claude requests it, returns the result (including rate-limit errors) as a `tool_result` block, and continues until Claude produces its final classification and draft reply. Cap the number of loop iterations. Update the system prompt to say refunds apply only to billing tickets and to tell the customer honestly if a refund was declined or limited.
6. Treat the model's arguments as untrusted: enforce the ticket id matches the ticket currently being triaged (so the model cannot refund another ticket), and make the call idempotent per ticket so a retried request cannot refund twice. Consider requiring human approval above a threshold amount rather than refunding automatically.
7. Add pytest tests: valid refund succeeds and is audited; invalid amount, unknown ticket, and mismatched ticket are rejected; the rate limit trips at the configured count and resets after the window; the tool-use loop handles a rate-limited result and the iteration cap. Mock the Anthropic client and use a test database.
8. Verify end to end by running the test suite and sending sample billing, bug, and how-to tickets through `POST /triage` against a test database, confirming refunds only occur on billing tickets, limits hold under repeated calls, and the audit log is complete. Document the new tool and its environment variables in `docs/` or the README.
