1. Define the tool schema for `issue_refund(ticket_id, amount)` in `app/triage.py` as a Claude tool definition (name, description, JSON input schema with ticket_id as string and amount as a positive number with a currency), and add it to the `tools` list on the existing Claude call. State in the description that the model may only request a refund and that a human or policy check decides.
2. Write a plain Python `issue_refund` function in a new `app/refunds.py` that performs the actual refund and records it in the database, plus an `execute_tool` dispatcher that maps the tool name from a `tool_use` block to this function, validating the arguments (ticket exists, amount is positive and not above the ticket's billed total).
3. Build the permission gate in code, not in the prompt: a `check_refund_permission(ticket_id, amount)` function that auto-approves only below a configured limit read from `config.py` (for example `REFUND_AUTO_LIMIT`), and otherwise returns "needs approval". Default to deny when anything is missing or ambiguous, and allow refunds only for tickets classified as billing.
4. Add a pending-approvals table and a `save_pending_refund` write so that requests above the limit are stored with status "pending" instead of executed. Add an authenticated `POST /refunds/{id}/approve` and `/deny` endpoint in `app/api.py` for a human reviewer, protected by an API key taken from an environment variable in `config.py`.
5. Extend the tool-use loop in `app/triage.py` so that when Claude returns a `tool_use` block for `issue_refund`, the code runs the gate first and sends back a `tool_result` that says "refunded", "pending human approval", or "denied" with a reason (using `is_error` for denials), then lets Claude finish drafting the reply based on that result. Cap the number of tool-use turns so the loop cannot run away.
6. Update the system prompt to tell Claude when refunds are appropriate (clear billing errors only), that it must never promise a refund in the draft reply before the tool result confirms it, and that a "pending" result must be phrased to the customer as under review. Treat the ticket text as untrusted so that a customer message cannot instruct the model to refund.
7. Write pytest tests in `tests/` with a mocked Anthropic client: an amount under the limit executes, an amount over the limit goes to pending, a non-billing ticket is denied, a bad or negative amount is rejected, a prompt-injection ticket does not trigger a refund, and the approve endpoint rejects a missing or wrong key. Also assert a refund is never executed twice for the same ticket.
8. Add an audit log entry for every refund request and decision (ticket_id, amount, who or what approved, timestamp), add a short help-doc note for support staff on the approval flow, and roll out first with a feature flag in `config.py` that keeps all refunds in "pending" until the team trusts the gate.
