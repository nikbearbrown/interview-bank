1. Define the tool contract first: add an `issue_refund(ticket_id, amount)` tool schema (typed ticket_id string, amount as a positive decimal with a currency and a hard maximum) in a new `app/tools.py`, and decide the rules it must enforce (ticket exists, is classified billing, amount does not exceed the original charge, no duplicate refund for the same ticket).
2. Build the audit log before the tool itself: create an append-only `refund_audit` table (and a small `app/audit.py` with `record_event(...)`) capturing timestamp, ticket_id, amount, who or what requested it (agent run id, model name), the inputs, the decision (approved, rejected, error) and the reason, so every attempt is recorded, including rejected ones.
3. Implement `issue_refund` as a thin wrapper around the real refund/payment call, with validation up front, an idempotency key derived from ticket_id and amount, and a rule that the audit record is written before the refund executes and updated with the outcome afterwards; if the audit write fails, the refund does not happen.
4. Add safety controls around the money action: a configurable per-refund cap and a daily total cap in `config.py`, a feature flag that is off by default, and a human-approval path (refunds above a threshold are queued as "pending approval" instead of executed), with payment credentials read only from environment variables.
5. Wire the tool into `app/triage.py` using the Anthropic SDK's tool-use loop: pass the tool definition to Claude, execute tool_use blocks in our code (never trust amounts blindly, re-check against the ticket data), return tool_result blocks, cap the number of loop iterations, and only expose the tool when the ticket is classified as billing.
6. Update the triage prompt so Claude knows when refunds are appropriate, must state its reason, and should prefer drafting a reply that offers a refund over issuing one when unsure; reference the relevant refund-policy help article in `docs/` rather than loading all 40 articles.
7. Write pytest tests in `tests/` using a mocked Anthropic client and a fake payment backend: valid refund, over-cap amount, duplicate call, non-billing ticket, audit-write failure blocking the refund, and a check that every path leaves exactly one audit entry; also add a prompt-injection case where the ticket text tries to demand a refund.
8. Roll out safely: run the new tests and the existing suite, deploy the container with the feature flag off, enable it in a dry-run mode that logs would-be refunds to the audit table only, review those entries, then turn on real refunds with the caps and monitor the audit log.
