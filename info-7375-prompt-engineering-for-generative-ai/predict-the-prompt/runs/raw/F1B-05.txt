1. Define the tool schema for `issue_refund` (ticket_id: string, amount: number, plus a short required `reason` field) in `app/triage.py` alongside the existing Claude call, with a description that says it only requests a refund and that a human must approve it before money moves. Add `refund_max_amount` and `refund_auto_approve_limit` settings to `config.py`, read from environment variables with safe defaults (auto-approve limit of zero).
2. Split the tool into two parts in a new `app/refunds.py`: the model-facing handler never executes the refund, it only validates input and writes a pending refund request (ticket_id, amount, reason, status="pending") through a new database function next to `save_reply`. A separate `execute_refund` function performs the actual payout and is callable only from the approval path.
3. Validate every call server-side before queuing it: the ticket must exist and be classified as billing, the amount must be positive, rounded to cents, no more than the ticket's charge, and under `refund_max_amount`, and the same ticket cannot already have a pending or completed refund. Reject invalid calls by returning an error tool_result so Claude can correct itself, and never trust the model's amount over the stored one.
4. Wire the tool into the Claude tool-use loop in `triage.py`: pass the tool definition, handle `tool_use` blocks by calling the queuing handler, return a tool_result such as "refund pending human approval", and let Claude finish drafting a reply that tells the customer the refund is under review rather than promising it. Cap the loop at a few iterations.
5. Build the approval gate in `app/api.py` with two new endpoints, `GET /refunds/pending` and `POST /refunds/{id}/approve` (plus `/reject`), protected by an approver credential or API key read from an environment variable. Approval re-validates the amount, atomically flips status from pending to approved so it cannot run twice, then calls `execute_refund` with an idempotency key and records who approved it and when; rejection records the reason.
6. Keep the safeguards outside the prompt: add an audit log row for every request, approval, rejection and execution, and make sure ticket text is treated as untrusted so a customer cannot talk the model into a refund (the gate, not the system prompt, is what enforces policy). Add one short instruction to the triage system prompt describing when to request a refund.
7. Write pytest tests in `tests/` with a mocked Anthropic client: a refund tool call creates only a pending record and moves no money; invalid, over-limit, duplicate and non-billing requests are rejected; approve executes exactly once and is idempotent on retry; unauthenticated approve calls fail; and a prompt-injection ticket still cannot bypass the gate.
8. Document the flow in one new help article in `docs/` for support staff (how pending refunds are reviewed and approved), note the new environment variables for the container, and roll out with the auto-approve limit at zero so every refund needs a human until the behavior has been observed in production.
