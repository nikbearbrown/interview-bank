1. Define the eval's scope and the acceptance criteria up front, before touching any prompt or code: classification accuracy on billing / bug / how-to (for example, at least 90% overall and at least 85% recall on each class), reply quality (no invented policies, refunds, or links; correct tone; answers the actual question), and a zero-tolerance rule that no ticket content may cause an unintended action or leak secrets.
2. Build a labeled golden dataset of roughly 150 to 300 real or realistic tickets (anonymized, PII stripped), balanced across the three classes, with extra slices for hard cases: ambiguous or multi-issue tickets, very short or very long tickets, non-English text, angry customers, and prompt-injection attempts embedded in ticket text. Have two people label each ticket and resolve disagreements, and keep a held-out set that is never used while tuning prompts.
3. Write a reference answer for the reply side: for how-to tickets, record which of the 40 docs/ articles should ground the answer, and for billing and bug tickets, record the facts a good reply must include or must avoid promising. Use these as rubric items rather than exact-match strings, since Claude's wording will vary.
4. Implement the eval as a pytest-driven harness in tests/ that calls the triage function with the Claude SDK (with save_reply stubbed so no database write occurs), runs each ticket several times at the production temperature and model, and records the predicted class, the draft reply, latency, and token usage. Pin the model version and prompt version in the run output so results are reproducible and comparable.
5. Score the classification automatically (accuracy, per-class precision and recall, confusion matrix, malformed or off-label output rate, with a target of zero unparseable outputs). Score the replies with a rubric-based Claude grader using a different, pinned grader prompt, plus deterministic checks (length limit, no secrets or system-prompt text, no URLs outside docs/), and spot-check a sample of grader verdicts by hand to confirm the grader is trustworthy.
6. Add consistency and robustness checks: the same ticket repeated should give the same class at least 95% of the time, injection tickets must never change the class to something unintended or cause extra behavior, and failures from API errors, timeouts, or empty replies must be handled gracefully with a bounded retry and a clear fallback.
7. Set pass/fail thresholds in config-free test code (secrets stay in environment variables only), make the eval fail the run if any acceptance criterion is missed, and write a short report listing every failed ticket with its input, expected result, and actual output so a human can review the misses.
8. Run the eval locally and in CI on a schedule and whenever app/triage.py, the prompt, or the model version changes, cap its cost and runtime with a budget, and keep the golden set versioned so new real-world failures get added as regression cases over time.
