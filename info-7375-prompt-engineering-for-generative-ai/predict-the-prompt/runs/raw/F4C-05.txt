1. Define the agent's contract: it takes a ticket and first produces a structured plan (classification, intended reply approach, the exact database write it intends to make, and any docs it needs), and it may not call `save_reply` until a human approves that plan. Reads and Claude calls are allowed in the planning phase; the database write is not.
2. Split `app/triage.py` into two stages: `plan_ticket(ticket)` and `execute_plan(plan)`. In the planning stage Claude, using the Anthropic Python SDK with a JSON-schema tool output, returns the category (billing / bug / how-to), the relevant help articles from `docs/` (chosen by title or keyword, not by loading all 40 articles), a draft reply, and a list of side effects it proposes.
3. Persist each plan as a pending record with an id, a status (pending, approved, rejected, executed), the ticket text, and a hash of the plan contents, so that approval is tied to exactly what the human saw and a later edit invalidates it. Keep this in the existing database, since the container has no other services.
4. Change `app/api.py` so `POST /triage` returns the plan with a plan id and status "pending" and writes nothing else. Add `GET /plans/{id}` for review and `POST /plans/{id}/approve` and `POST /plans/{id}/reject` (with an optional edited reply and a reason), protected by a reviewer credential read from an environment variable in `config.py`.
5. Make execution gated in code, not just in the prompt: `execute_plan` verifies the status is approved and the hash matches, then calls `save_reply(ticket_id, text)` once, marks the plan executed, and is idempotent so a repeated approve call cannot write twice. Rejected or edited plans cause re-planning or a human-written reply instead of an automatic write.
6. Write the planning prompt so Claude states its steps before acting, says what it is unsure about (for example, an ambiguous category or a billing issue that needs account data it lacks), and treats the ticket text as untrusted data rather than instructions. Set low-confidence or sensitive tickets (refunds, legal, account closure) to be flagged for closer review.
7. Add pytest tests in `tests/` with the Claude client mocked: planning never calls `save_reply`; an unapproved or rejected plan cannot execute; an edited plan after approval is refused; double approval writes once; and the plan output matches the schema. Add a small set of recorded sample tickets to check classification and the choice of docs.
8. Roll it out behind a config flag with all tickets requiring approval at first, log plan, approval, and execution events (without secrets or full customer text), and review approval and edit rates after a trial period to decide whether any low-risk category could later be auto-approved.
