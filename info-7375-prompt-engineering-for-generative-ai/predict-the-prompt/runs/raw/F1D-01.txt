1. Define the refund tool schema for Claude in app/triage.py: a tool named `issue_refund` with `ticket_id` (string) and `amount` (number, positive, currency specified) and a clear description saying it should be used only when the ticket is a billing issue that justifies a refund. Add the tool to the Anthropic SDK `tools` list on the triage call.
2. Write the audit log first: add a small append-only audit module (e.g. app/audit.py) that records every refund attempt with timestamp, ticket_id, amount, model/request id, the model's stated reason, and outcome (approved, rejected, failed). Store it in a dedicated audit table in the existing database, written in the same flow so a refund cannot happen without a log entry.
3. Implement `issue_refund(ticket_id, amount)` as a Python function that validates inputs (ticket exists, is classified as billing, amount > 0 and under a configurable cap and not above the original charge, no duplicate refund for the ticket), logs the attempt to the audit log before calling the payment backend, then logs the result. Put the cap and any enable flag in config.py, with payment credentials read from environment variables.
4. Add a guard layer between Claude and the function: Claude's tool call is only a request, so the code enforces the rules and, for amounts above a threshold, returns a "pending human approval" result instead of executing. Never trust the model-supplied amount without server-side checks.
5. Extend the tool-use loop in app/triage.py: when the response contains a `tool_use` block for `issue_refund`, run the guarded function, send the result back as a `tool_result` block (including errors and rejections), and continue until Claude returns its final reply; cap the number of loop iterations. Then save the reply with `save_reply` as before.
6. Update the system prompt so Claude knows when to propose a refund, that it must state a reason, and that rejected or pending results must be communicated honestly in the drafted reply instead of promising money.
7. Write pytest tests with the Anthropic client mocked: a valid refund is executed and logged, an over-cap or non-billing request is rejected and still logged, a duplicate is blocked, a failed payment call is logged as failed, and the audit entry exists in every case. Add a test for the loop limit and for the `POST /triage` endpoint end to end.
8. Roll out safely: ship with the tool disabled by a config flag or in dry-run mode (logging only) first, review the audit log against real tickets, then enable real refunds. Add a short help-docs or runbook note on how to read the audit log, and make sure the log is included in the container's persistent database and never deleted by the app.
