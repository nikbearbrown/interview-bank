1. Define the tool contract first: add an `issue_refund(ticket_id, amount)` tool schema (name, description, typed input_schema with ticket_id as string and amount as a positive number with a hard maximum) to a new `app/tools.py`, and write the handler that performs the refund and records it in the database.
2. Validate inside the handler, never trusting the model's arguments: check that the ticket exists, is classified as billing, has not already been refunded, and that amount is positive and does not exceed the original charge or a configured per-refund cap.
3. Add the rate limit as a server-side check in the handler, independent of the prompt: a per-ticket limit (one refund) plus a global limit (for example N refunds per hour), backed by a small `refund_log` table in the existing database so it survives restarts and works in a single container. Return a clear "rate limit exceeded" tool result rather than raising when the limit is hit.
4. Put the limits in `config.py` (max amount, per-hour count, a kill-switch flag to disable refunds), read from environment variables with safe defaults, so they can be tuned without a code change.
5. Wire the tool into `app/triage.py`: pass it in the `tools` parameter of the Claude call, and add a tool-use loop that executes `issue_refund` calls, returns `tool_result` blocks (including error results for denied or rate-limited calls) and continues until Claude gives its final reply, with a maximum number of iterations.
6. Update the system prompt to say when the tool may be used (only for clear billing refund requests), that it must mention the refund in the drafted reply, and that a rate-limit or validation error means it should escalate to a human instead of retrying.
7. Add pytest tests in `tests/` with a mocked Anthropic client: successful refund, over-cap amount, duplicate refund, global and per-ticket rate-limit hits, non-billing ticket, and the tool loop's iteration cap; also a test that `POST /triage` still works with no refund.
8. Log every refund attempt (ticket_id, amount, outcome) for auditing, then roll out behind the kill-switch flag, enabling it in the container's environment once the tests pass and a manual check against a test ticket looks right.
