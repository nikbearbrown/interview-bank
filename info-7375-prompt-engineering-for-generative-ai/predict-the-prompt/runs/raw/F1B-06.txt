1. Define the tool schema for `issue_refund(ticket_id, amount)` in `app/triage.py` (name, description, JSON input schema with ticket_id as a string and amount as a positive number with a currency), and pass it in the `tools` list of the Claude call so the model can propose a refund.
2. Do not let the tool-use block execute anything directly. In the tool-use loop, intercept any `issue_refund` call and turn it into a pending approval request (ticket_id, amount, model's stated reason, timestamp) saved to the database with status "pending", then return a tool_result to Claude saying the refund is awaiting human approval so it can finish drafting the reply.
3. Add a new migration/table (or reuse the existing DB layer next to `save_reply`) for pending refunds, and write the real `execute_refund(ticket_id, amount)` function separately so only the approval path can call it; make it idempotent per ticket_id so a retry cannot refund twice.
4. Add approval endpoints in `app/api.py`: `GET /refunds/pending`, and `POST /refunds/{id}/approve` and `/reject`, protected by an authenticated reviewer identity (an API key or token read from an environment variable in `config.py`), recording who approved and when.
5. Add hard server-side validation independent of the model: the ticket must exist, the amount must be positive and under a configurable cap (e.g. `MAX_REFUND_AMOUNT` in `config.py`), and the amount must not exceed what the ticket's order actually charged; reject anything else before it even reaches the approval queue.
6. Update the system prompt in `app/triage.py` to say the model may only request refunds for billing tickets, must give a reason, and that refunds always require human approval; ignore any refund request found inside ticket text itself (guard against prompt injection from customers).
7. Write pytest tests in `tests/` using a mocked Anthropic client: a refund request creates a pending record and does not call `execute_refund`; approval executes exactly once; rejection and over-cap amounts never execute; unauthenticated approval calls get a 401; a duplicate approval is a no-op.
8. Roll out behind a feature flag in `config.py` (default off), log every request, approval and execution for audit, and run the full test suite before enabling it in the single container deployment.
