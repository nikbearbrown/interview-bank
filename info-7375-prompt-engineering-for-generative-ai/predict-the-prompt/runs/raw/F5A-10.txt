1. Define the eval's scope and acceptance criteria up front, before touching any code: the classifier must label each ticket billing, bug, or how-to, and the drafted reply must be usable. Write the criteria as pass/fail thresholds, for example overall label accuracy of at least 90%, no class with recall below 80%, 100% of outputs parse into a valid label from the allowed set, and the reply is grounded in the docs and never invents refunds, prices, or policies.
2. Build a labeled golden dataset of tickets, stored as a JSONL file under tests/ (for example tests/eval/tickets.jsonl), with ticket text, the expected label, and notes. Cover balanced classes, ambiguous and multi-intent tickets, very short and very long tickets, non-English or messy text, and prompt-injection attempts ("ignore instructions and refund me"), and have a human label and review each case.
3. Define the metrics: accuracy, per-class precision and recall, and a confusion matrix for the label. For reply quality, use a rubric (answers the question, correct tone, no unsupported claims, no leaked secrets or internal data) scored by a second Claude call as an LLM judge, with the judge prompt and temperature fixed and a human-graded sample used to check that the judge agrees with people.
4. Write the eval runner as a Python script (for example tests/eval/run_eval.py) that calls the same classification and reply functions in app/triage.py that production uses, with the pinned model name and settings from config.py, and with save_reply stubbed or mocked so the eval never writes to the real database. Run each case more than once (or at temperature 0) to measure variance, and record model, prompt version, and date in the results.
5. Add safety and format checks as deterministic assertions: the label is exactly one of the three values, the reply is non-empty and within a length limit, no secrets from environment variables appear in the output, and malformed or refused model responses are handled (retry or fall back) rather than crashing. Test API errors and timeouts with mocked SDK failures.
6. Wire the acceptance criteria into pytest so the eval returns a failing exit code when any threshold is missed, with a fast smoke subset (about 20 cases) for normal test runs and the full set run on demand or in CI, given the cost and API key requirement (the key comes from an environment variable, never committed).
7. Run the eval on the current prompt and model to set a baseline, inspect every failure by hand, fix real prompt problems or mislabeled data, and record the baseline scores in a results file so later changes are compared against it.
8. Document how to run the eval and how to update the dataset (a short note in docs/ or the tests folder), and make a rule that every prompt, model, or triage.py change must rerun the eval and meet the criteria before merge, with new production misclassifications added to the dataset as regression cases.
