1. Define the tool contract first: `issue_refund(ticket_id, amount)` returns a structured result (refunded / rejected with a reason / rate-limited), and write its JSON schema for Claude with a precise description of when it may be used (billing tickets only, amount in the ticket's currency, never above the amount the customer paid).
2. Add a new module (e.g. `app/refunds.py`) holding the real `issue_refund` function. It validates its inputs (ticket exists, ticket classified as billing, amount positive and within a configured cap) and performs the refund through whatever payment path the service already uses, recording each refund in the database alongside `save_reply`.
3. Implement the rate limit in code, outside the model, so Claude cannot talk its way around it. Track refund counts and total refunded amount per time window (for example per ticket, per customer, and globally per hour) in the database, since the service is a single container with no other services, and reject calls over the limits with a clear "rate limited" result.
4. Put the limits in `config.py` (max refunds per window, max amount per refund, window length), read from environment variables with safe defaults, so they can be tuned per deployment without a code change.
5. Wire the tool into `app/triage.py`: pass the tool definition in the Anthropic SDK call and add a tool-use loop that executes `issue_refund` when Claude requests it, returns the result as a `tool_result` block, and caps the number of loop iterations. Update the system prompt to say that refunds are limited and that a rejected or rate-limited result means the ticket should be escalated to a human in the drafted reply, not retried.
6. Make the refund idempotent and auditable: key it on `ticket_id` so a retried `POST /triage` cannot refund the same ticket twice, and log every attempt (allowed or rejected) with ticket id, amount, and reason.
7. Add pytest tests in `tests/` with the Claude client mocked: a valid refund succeeds, an over-cap amount is rejected, the Nth call within the window is rate limited, a duplicate call for the same ticket is not refunded twice, and the tool-use loop handles a rate-limited result by drafting an escalation reply.
8. Run the full test suite, then try `POST /triage` locally against a few sample tickets (including one that should trigger a refund and one that should hit the limit), and document the new tool, its limits, and the config variables in a short `docs/` note for operators before deploying the container.
