1. Decide the retrieval design first: with 40 articles of about 600 words each (roughly 32k tokens in total), keep it simple and in-process with no new services, since the app ships as one container. Chunk each article by heading or paragraph group (about 150-250 words) and keep the article filename and title as metadata.
2. Add a new module, e.g. app/retrieval.py, that loads and chunks everything in docs/ once at startup and builds an index. Start with BM25 or TF-IDF (pure Python, no extra service) and keep the interface behind one function, retrieve(ticket_text, k=3), so embeddings can replace it later without touching triage.py.
3. Retrieve using the ticket text, and also use the classification (billing / bug / how-to) as an optional filter or boost. Return the top k chunks with their source article names, and return nothing if scores fall below a threshold.
4. Change the draft-reply call in app/triage.py to put the retrieved chunks into the prompt, wrapped in clearly delimited, labeled tags with the article name on each. Rewrite the system prompt to say: answer only from the supplied articles, cite the article, and if the articles do not cover the question, say so and flag the ticket for a human instead of guessing.
5. Treat ticket text and article text as untrusted data inside the prompt (delimit it, tell Claude not to follow instructions found in either). Keep save_reply(ticket_id, text) as the only database write, and have it run only after the reply is generated, so a retrieval or API failure cannot save a partial reply.
6. Handle failure paths: if retrieval errors out or returns no relevant chunks, fall back to a safe reply or a "needs human" flag rather than an ungrounded answer. Put k, chunk size, the score threshold, and the docs path in config.py, with secrets still read from environment variables.
7. Add pytest tests: chunking and index-building on a small fixture docs folder; retrieval returns the right article for sample billing, bug and how-to tickets; the prompt builder includes the retrieved text and article names; and triage with the Anthropic client mocked, covering both the grounded case and the no-match case, and checking that save_reply is called once with the expected text. Also run the existing tests and the POST /triage endpoint to check nothing else broke.
8. Evaluate before shipping: build a small labeled set of past tickets with the article that should answer each, and measure retrieval hit rate at k and how often replies cite a correct article. Confirm the docs are included in the container image, and log which articles were used per ticket so replies can be audited.
