1. Define the routing contract: a fixed set of ticket types (billing / bug / how-to) mapped to named handlers or queues, plus a Pydantic model for a "plan" (ordered steps, the ticket ID, the chosen route, which docs to consult, which writes it intends to make, and a confidence note).
2. Add a planning stage in `app/triage.py` that calls Claude with the ticket text and the route list and asks for a plan only, returned as structured JSON validated against the Pydantic model, with no tool access to anything that writes.
3. Keep every side effect (including `save_reply`, which is the one database write) out of the planning stage, so the agent can propose actions but cannot execute them until a human has approved.
4. Store each pending plan with a status (pending / approved / rejected / edited) and an expiry, keyed to the ticket ID, in the existing database, since the service is a single container with no other services.
5. Add API endpoints in `app/api.py`: `POST /triage` now returns a plan and a plan ID, and a new approval endpoint accepts approve / reject / edit-and-approve from a reviewer, checks the reviewer's identity against a credential read from an environment variable via `config.py`, and refuses to proceed if the plan is not in the pending state.
6. Add an execution stage that runs only on an approved plan: it re-validates the stored plan, has Claude draft the reply (pulling in relevant articles from the 40 docs), calls `save_reply`, and records who approved it and when; rejected or expired plans do nothing.
7. Put guardrails around it: a step limit, a timeout, handling of API errors and malformed model output (retry once, then route the ticket to a human), and logging of every plan, decision, and execution without writing secrets or full ticket text.
8. Write pytest tests with the Claude client mocked, covering that nothing is written before approval, that rejection and expiry block execution, that an edited plan runs as edited, that malformed plans are caught, and that approving the same plan twice writes only once; then update `docs/` with a short description of the approval flow.
