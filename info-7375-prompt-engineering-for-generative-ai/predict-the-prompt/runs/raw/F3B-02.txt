1. Add a small loader in app/ (for example app/kb.py) that reads all 40 markdown files from docs/ in sorted order once at startup, wraps each in a labelled block (article id/filename and title) and joins them into one knowledge-base string held in memory.
2. Measure the size: use the Anthropic SDK token-counting call on the assembled text (roughly 24,000 words, so about 30-35k tokens) and confirm it fits comfortably within the model's context window alongside the ticket and the reply; add a startup check that fails loudly if docs/ is missing or the count is unexpectedly small.
3. In app/triage.py, build the system prompt as two parts: the fixed instructions (classify as billing / bug / how-to, draft a reply, answer only from the articles, say so and escalate when the answer is not in them, cite the article id used) followed by the knowledge-base block. Keep the ticket text in the user message so the system prompt stays identical across requests.
4. Mark the system prompt's knowledge-base block with cache_control so prompt caching makes repeated calls cheap and fast; keep the block byte-for-byte stable (sorted order, no timestamps) so the cache actually hits, and log cache read/creation tokens from the response usage.
5. Have the model return a structured result (category, reply text, list of cited article ids) and validate it in code; if a cited id is not one of the 40 loaded articles, or the reply cites nothing, treat the draft as ungrounded and flag it instead of silently saving it.
6. Only call save_reply(ticket_id, text) after validation passes, and keep the config.py settings (model name, max tokens, docs path) and the API key from environment variables, with no secrets in the prompt or the docs loader.
7. Add pytest tests with the Anthropic client mocked: the loader returns all 40 articles in a stable order, the system prompt contains every article and the cache marker, the validation rejects unknown citations, and the existing POST /triage behaviour in app/api.py is unchanged. Add one small opt-in live test with a few sample tickets whose answers are known to be in specific articles.
8. Run the test suite, try a handful of real tickets (including one that no article covers) to check that answers come from the docs and that out-of-scope tickets get an escalation, then check the container build still includes docs/ so the deployed service can read them.
