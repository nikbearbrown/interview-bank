## The ten-second version

- A model is a function with learned weights; a prompt never changes the weights.
- A language model predicts the next token; it can be fluent and wrong.
- Self-attention learns context; positional encoding adds order; an embedding captures meaning from use.
- Format validity is not factual validity: a green check shows the shape passed.
- An agent loop is a model proposing and a controller acting, observing and feeding back.
- Evidence is something you can confirm without asking the producer. A receipt the agent hands back is still its claim.
- You sign it, you own it. Using AI to work faster is fine; once you let it decide and you sign, the result is yours, not the AI's.
- An agent's account of itself is not a record. The agent sees only its context; you see only the trace you kept.
- Activity is not progress. Name a measure of progress, record it, and check it; a turn budget caps turns, it does not measure progress.
- MCP answers interoperability (can we exchange messages?), not authorization (should we use this?). A person decides which servers connect.
- Retrieval changes what the model sees; fine-tuning changes the model. Behavior in the weights, knowledge in the context.
- Frontier training data is a very large filtered slice of text, not "the entire internet".
- A progress bar is completion, not progress. Progress is the job working: validation loss falling and outputs improving.
- Tune on validation data, never on the test set; keep every trial.
- A token is a password: browser login, never pasted, never in a chat or a script.

## Part A: How a language model works

**1. Model and language model.** A model is a function from input to output whose parameters (weights) are learned from data. A language model gives a probability for the next token given the tokens so far. Text comes out by predicting, sampling one token, appending it and repeating (autoregressive). Sending a prompt does not change the weights; changing a prompt, context or setting is not training.
Go to: [chapter 1](https://github.com/nikbearbrown/info-7375-prompt-engineering-for-generative-ai/blob/main/chapters/01-next-token-prediction-and-sampling.md)
Practice: foundations MA-2.1, MA-2.2, ES-2.1; MA-1.1, MA-1.2, ES-1.1 (why models improved)

**2. Tokens and embeddings.** Text is split into tokens, which are not always words, and each token is looked up as an embedding, a vector of numbers. A token ID is only a label. An embedding captures meaning because words that are reasonable predictions in the same context end up close ("I walk my Labrador" and "I walk my sheepdog"). One-hot vectors are huge and sparse and make every word equally far from every other; alphabetical numbering is spelling, not meaning. Embeddings squeeze a vocabulary of tens of thousands into about a thousand numbers: they keep meaning efficiently, are lossy, and keep biases.
Go to: [chapter 1](https://github.com/nikbearbrown/info-7375-prompt-engineering-for-generative-ai/blob/main/chapters/01-next-token-prediction-and-sampling.md)
Practice: foundations MA-4.1 to MA-4.7, ES-4.1 to ES-4.6

**3. The transformer, at overview depth.** Two parts: one learns the context with self-attention, the other predicts next-token probabilities. Self-attention lets each token weigh the others. Positional encoding adds word order, which attention alone lacks. An encoder reads; a decoder produces. A feedforward network (multi-layer perceptron) is the common way a network turns inputs into predictions. Transformers train in parallel, which matters at internet scale, but generate one token at a time.
Go to: [chapter 1](https://github.com/nikbearbrown/info-7375-prompt-engineering-for-generative-ai/blob/main/chapters/01-next-token-prediction-and-sampling.md)
Practice: foundations MA-3.1 to MA-3.4, MA-6.1 to MA-6.4, ES-3.1 to ES-3.3, ES-6.1 to ES-6.3

**4. Softmax and temperature.** Logits are raw scores, one per vocabulary token. Softmax turns them into probabilities that sum to one. A lower temperature sharpens them (more repeatable); a higher one flattens them (more varied). Sampling means the same prompt can give different answers.
Go to: [chapter 1](https://github.com/nikbearbrown/info-7375-prompt-engineering-for-generative-ai/blob/main/chapters/01-next-token-prediction-and-sampling.md)
Practice: foundations MA-5.1 to MA-5.3, ES-5.1; ch01

**5. Programs versus language models.** A program does exactly what its rules say; a language model predicts likely text. A well-written pure function is checkable, repeatable and testable. A sound design rule: let the model generate and let ordinary code check.
Go to: [chapter 2](https://github.com/nikbearbrown/info-7375-prompt-engineering-for-generative-ai/blob/main/chapters/02-prompt-contracts-and-evaluation.md)
Practice: foundations MA-7.1, MA-7.2, MA-8.1, MA-8.2, ES-7.1, ES-8.1

## Part B: The gate and checking

**6. Division of labor, the gate and the sign-off.** AI can draft, compute, retrieve, test and challenge. Humans decide, check and own the result. A gate is a check or human decision an output must pass before it is accepted or acted on; you write it before you ask for anything. Three jobs stay with you: conduct (decide before it runs), check (what would show it is wrong, who checked, what nobody checked) and drive (you sign what you keep). Using AI to work faster is fine. Once you let it decide and you sign, the result is yours, not the AI's. A sign-off says what was checked, how, what was not checked, what is not claimed, and whether you signed or withheld; the AI can draft its words fluently, but the content has to come from your own record.
Go to: [chapter 1](https://github.com/nikbearbrown/info-7375-prompt-engineering-for-generative-ai/blob/main/chapters/01-next-token-prediction-and-sampling.md), [chapter 2](https://github.com/nikbearbrown/info-7375-prompt-engineering-for-generative-ai/blob/main/chapters/02-prompt-contracts-and-evaluation.md), [chapter 6](https://github.com/nikbearbrown/info-7375-prompt-engineering-for-generative-ai/blob/main/chapters/06-claude-code-and-diff-review.md), [chapter 13](https://github.com/nikbearbrown/info-7375-prompt-engineering-for-generative-ai/blob/main/chapters/13-evaluation-and-approval-gates.md), [chapter 15](https://github.com/nikbearbrown/info-7375-prompt-engineering-for-generative-ai/blob/main/chapters/15-supervised-capstone.md)
Practice: foundations MA-9.1 to MA-9.3, ES-9.1, ES-9.2; ch13

**7. Format validity is not factual validity.** Valid JSON can hold a false answer. A validator checks the shape, not whether the claim is true. One prompt run three times gives three samples, not a measurement. Validation and verification are separated in item 44.
Go to: [chapter 2](https://github.com/nikbearbrown/info-7375-prompt-engineering-for-generative-ai/blob/main/chapters/02-prompt-contracts-and-evaluation.md)
Practice: foundations MA-10.1 to MA-10.3, ES-10.1, ES-10.2

## Part C: Agents and verification

**8. The agent loop.** A policy (the model) proposes the next action; a controller (the program around it) runs it, observes the result and feeds it back; the loop repeats until a stop. A system that can search, read files or run code is acting; one that only returns text is not, even with the same model. There is more than one agent loop, so when one is described, read its steps: who proposes, who runs, what comes back to the model, who holds the stop, the unit of the budget, and the exits. In some loops the result is fed back to the model; in others it is only recorded. "Finished" means the loop returned, not that the answer is right.
Go to: [chapter 4](https://github.com/nikbearbrown/info-7375-prompt-engineering-for-generative-ai/blob/main/chapters/04-the-agent-loop.md), [chapter 11](https://github.com/nikbearbrown/info-7375-prompt-engineering-for-generative-ai/blob/main/chapters/11-tool-use-and-verification.md)
Practice: foundations MA-11.1, MA-11.2, ES-11.1; ch04

**9. Solve-verify asymmetry, fluency, falsifiability.** Some things are easier to check than to produce, and a designer can use that to build generate-then-check systems. Fluent is not correct. A claim must be able to be shown wrong: "the prompt is better" becomes falsifiable only with a stated test.
Go to: [chapter 2](https://github.com/nikbearbrown/info-7375-prompt-engineering-for-generative-ai/blob/main/chapters/02-prompt-contracts-and-evaluation.md), [chapter 11](https://github.com/nikbearbrown/info-7375-prompt-engineering-for-generative-ai/blob/main/chapters/11-tool-use-and-verification.md)
Practice: foundations MA-12.1 to MA-12.3, ES-12.1, ES-12.2

**10. Evidence you can check independently.** An agent's claim is testimony. Evidence is something a checker can confirm without going through the producer: a reference id looked up at the system of record, a source location, a re-run test. A receipt the agent returns is an artifact it controls until someone verifies it at the payment system. Asking the same kind of model to confirm its own answer gives correlated errors. How much evidence you need scales with the consequence. Independence comes in degrees: a check is independent to the degree that it fails differently from what it checks, so two language models can share the same blind spots; audit a generative claim with a non-generative tool such as ordinary code or a lookup. The degree of the check should match how bad it is to be wrong (item 33).
Go to: [chapter 11](https://github.com/nikbearbrown/info-7375-prompt-engineering-for-generative-ai/blob/main/chapters/11-tool-use-and-verification.md), [chapter 12](https://github.com/nikbearbrown/info-7375-prompt-engineering-for-generative-ai/blob/main/chapters/12-memory-and-multiple-agents.md), [chapter 10](https://github.com/nikbearbrown/info-7375-prompt-engineering-for-generative-ai/blob/main/chapters/10-planning-before-acting.md)
Practice: ch11, ch12

**11. Need to know.** Give an agent only the information and the tools its task needs: less to leak, less damage when it is wrong, less clutter. It covers tool and data access, not just the prompt. A person decides what the task needs. Capability is what a system is able to do (for example reason, read, write). Limiting capability limits scope: grant what the task needs, not the most you can, because every extra operation is one more thing to check afterward. Capability is not authority: being able to do something is not permission to. If an agent given write access alters a file it only needed to read, the failure is the grant, made before anything ran.
Go to: [chapter 3](https://github.com/nikbearbrown/info-7375-prompt-engineering-for-generative-ai/blob/main/chapters/03-chat-assistant-agent.md), [chapter 5](https://github.com/nikbearbrown/info-7375-prompt-engineering-for-generative-ai/blob/main/chapters/05-tools-and-permissions.md), [chapter 12](https://github.com/nikbearbrown/info-7375-prompt-engineering-for-generative-ai/blob/main/chapters/12-memory-and-multiple-agents.md), [chapter 15](https://github.com/nikbearbrown/info-7375-prompt-engineering-for-generative-ai/blob/main/chapters/15-supervised-capstone.md)
Practice: MA-ch05.62†, ES-ch05.62†, MA-ch12.61†; ch05

## Part D: Retrieval, tools and MCP

**12. Retrieval (RAG).** Look up relevant passages, put them in the prompt, then generate. It does not retrain the model and does not guarantee correct answers: retrieval ranks by similarity and can miss or mis-rank. An API call is exact; retrieval is approximate. Use retrieved or system-of-record facts for private, current or exact things; a model can propose steps and order, but facts about the real system must be observed and a plan is reviewed before acting.
Go to: [chapter 7](https://github.com/nikbearbrown/info-7375-prompt-engineering-for-generative-ai/blob/main/chapters/07-retrieval-and-cowork.md), [chapter 10](https://github.com/nikbearbrown/info-7375-prompt-engineering-for-generative-ai/blob/main/chapters/10-planning-before-acting.md)
Practice: ch07; MA-ch07.64†, MA-ch07.65†, ES-ch07.60†, MA-ch10.64†, MA-ch10.65†, ES-ch10.61†

**13. What MCP is.** The Model Context Protocol is an open standard that connects an AI application (the host, through a client) to tools and data (a server). Messages are JSON-RPC 2.0; local servers talk over standard input and output, remote ones over HTTP. A server can offer tools (model-controlled), resources (application-controlled) and prompts (user-controlled). In the course's version (protocol 2025-11-25) the order is: initialize, then the initialized notification, then ordinary requests such as tools/list and tools/call; a request made too early is rejected. **Name the version in an answer**: newer revisions change the handshake.
Go to: [chapter 8](https://github.com/nikbearbrown/info-7375-prompt-engineering-for-generative-ai/blob/main/chapters/08-mcp-from-scratch.md), [the MCP specification](https://modelcontextprotocol.io)
Practice: ch08 (MA-ch08.1 to MA-ch08.64, ES-ch08.1 to ES-ch08.60)

**14. MCP is not trust.** MCP answers interoperability, not authorization. A valid handshake is not a trust signal. A tool's description is the server's own claim, and it is text the model reads, so misleading text can steer the model. A JSON-RPC error means the protocol failed; a tool result with isError true means the call ran and the tool reported a failure. A person decides which servers are connected.
Go to: [chapter 8](https://github.com/nikbearbrown/info-7375-prompt-engineering-for-generative-ai/blob/main/chapters/08-mcp-from-scratch.md)
Practice: ch08

**15. Discover, decide, invoke.** MCP standardizes discovery (the client asks what the server offers, so a model can learn tools that appeared after its training) and invocation. Whether this server belongs in this task stays with a person. The human chooses servers, sets which tools are allowed and when to ask; the agent picks the tool, the arguments and the order; the host enforces the human's policy. Verifying a result is a further step: a signature shows who sent it, not that it is correct.
Go to: [chapter 8](https://github.com/nikbearbrown/info-7375-prompt-engineering-for-generative-ai/blob/main/chapters/08-mcp-from-scratch.md)
Practice: ch08

**16. MCP, APIs, REST, function calling and the command line.** An API is any agreed way for one program to use another. REST is one style of web API: resources named by URLs, HTTP verbs as actions, stateless requests, usually JSON. HTTP is the protocol it rides on. Function calling is how a model asks for a tool, and something still has to run it. MCP is a standard way to discover and run tools; servers usually wrap APIs, so it does not replace REST or function calling. Costs of MCP: tool descriptions use context, each server is more code to trust, and the standard keeps changing. For an agent with a shell, a command-line tool is often simpler.
Go to: [chapter 8](https://github.com/nikbearbrown/info-7375-prompt-engineering-for-generative-ai/blob/main/chapters/08-mcp-from-scratch.md), [chapter 7](https://github.com/nikbearbrown/info-7375-prompt-engineering-for-generative-ai/blob/main/chapters/07-retrieval-and-cowork.md)
Practice: ch08, ch07

**17. Agents talking to agents.** A2A lets one agent hand work to another; MCP connects an agent to tools and context. The design question is whether to do the task or delegate it, and what comes back. Keep three questions apart: who is this agent (identity), may it have this task and information (authorization), and did it do the work correctly (correctness, which only evidence answers). Delegating does not hand off responsibility.
Go to: [chapter 12](https://github.com/nikbearbrown/info-7375-prompt-engineering-for-generative-ai/blob/main/chapters/12-memory-and-multiple-agents.md)
Practice: ch12

**18. Giving a model information it does not have.** A model knows what its training data held, up to a cutoff. Frontier training data is a very large but filtered slice of text (blocked, login-gated and duplicate pages are left out; licensed and synthetic data are added), not "the entire internet" *(this description rests on secondary summaries of model documentation; not checked against the primary documents)*. New information reaches a model through its input: pasted text or a screenshot, a search, a fetched page, retrieval, or a connected tool. None of these changes the weights. A cited answer is not verified, a site can block the tool's crawler, and a person chooses the sources.
Go to: [chapter 7](https://github.com/nikbearbrown/info-7375-prompt-engineering-for-generative-ai/blob/main/chapters/07-retrieval-and-cowork.md), [chapter 8](https://github.com/nikbearbrown/info-7375-prompt-engineering-for-generative-ai/blob/main/chapters/08-mcp-from-scratch.md)
Practice: MA-2.3†, MA-2.4†, ES-2.2†

## Part E: Training and fine-tuning

**19. Five things a system can change.** Weights, prompt, context, tools and settings. Only the weights involve an optimizer. A saved prompt, a stored document, a permission rule and a memory record all persist, and none of them is training. Training is identified by its mechanism: labels and a loss-derived gradient changing parameters. The test: change one object, hold the rest fixed, and watch.
Go to: [chapter 9](https://github.com/nikbearbrown/info-7375-prompt-engineering-for-generative-ai/blob/main/chapters/09-training-and-configuration.md), [lesson 9](https://github.com/nikbearbrown/info-7375-prompt-engineering-for-generative-ai/blob/main/lessons/09-training-and-configuration/docs/en.md)
Practice: ch09

**20. Held-out data, loss and what you may claim.** Training, development and held-out data have different roles; held-out data is touched once, after every choice is fixed. A lower training loss supports one claim: the objective fell on the examples shown. It does not show the model fits unseen data or that the objective was the right one. Prediction is not intervention: a fitted model answers "what will it say", not "what happens if we act". "Lowered the objective" and "learned" (a parameter change) are accurate verbs; "generalizes" needs a held-out result; "causes" needs assumptions the data cannot supply.
Go to: [chapter 9](https://github.com/nikbearbrown/info-7375-prompt-engineering-for-generative-ai/blob/main/chapters/09-training-and-configuration.md)
Practice: ch09

**21. What fine-tuning is, and how it works.** Optimization is choosing parameter values that make a loss (a number that scores how wrong the model is on the examples) as small as possible. The optimizer is the procedure that does it, usually gradient descent: measure the loss, compute the gradient (the direction that lowers it), take a small step, repeat. The optimizer lowers whatever objective you give it, so the objective is a choice. Fine-tuning applies this: continue training an already-trained model on a small, targeted set so its weights shift: start from pretrained weights, collect example pairs (or better-and-worse pairs), choose an objective (a loss), run predict, measure the loss, compute the gradient, update, at a small learning rate for a few passes, then check on held-out examples and keep the result as a new artifact. It suits style, format, a narrow skill and consistency. It is a poor way to add a lot of fresh or changing facts, and it does not learn from a chat. Risks: overfitting, forgetting other abilities, flawed examples baked in.
Go to: [chapter 9](https://github.com/nikbearbrown/info-7375-prompt-engineering-for-generative-ai/blob/main/chapters/09-training-and-configuration.md), [the LoRA paper](https://arxiv.org/abs/2106.09685)
Practice: none yet

**22. Fine-tuning, retrieval or a system prompt.** Fine-tuning changes the model; retrieval changes what the model sees this turn; a system prompt is standing instructions in the context. Behavior goes in the weights, knowledge in the context. Try the cheap and reversible first: prompt, then context, then tools, then fine-tuning. Retrieval can cite its sources and update instantly; fine-tuned knowledge cannot be traced or easily removed. Many small models (such as T5) have no system prompt at all: just an input and an output.
Go to: [chapter 9](https://github.com/nikbearbrown/info-7375-prompt-engineering-for-generative-ai/blob/main/chapters/09-training-and-configuration.md), [chapter 7](https://github.com/nikbearbrown/info-7375-prompt-engineering-for-generative-ai/blob/main/chapters/07-retrieval-and-cowork.md)
Practice: none yet

**23. Why customize.** Fine-tuning can give a model your voice, your drawing hand or your writing style: things you show, not describe. Train only on your own work or with written consent, say when a voice or an image is synthetic, and guard the weights like a password. For a portfolio piece, the evidence is what counts, not the score.
Go to: [chapter 9](https://github.com/nikbearbrown/info-7375-prompt-engineering-for-generative-ai/blob/main/chapters/09-training-and-configuration.md)
Practice: none yet

**24. Hyperparameters.** Settings you choose that control training; the gradient does not learn them. The main ones: learning rate (the most important, with its schedule: too large can overshoot or go unstable, too small makes progress slow, and no value is safe for every task), batch size, epochs or steps with early stopping, optimizer settings (weight decay, gradient clipping), dropout, sequence length, numeric precision and the random seed; for LoRA also the rank, a scaling factor and which layers. Tune on validation data, never the test set; change one thing at a time; random search often matches a grid with fewer runs *(not checked)*; keep every trial; a difference smaller than the gap between two seeds means nothing.
Go to: [chapter 9](https://github.com/nikbearbrown/info-7375-prompt-engineering-for-generative-ai/blob/main/chapters/09-training-and-configuration.md), [the QLoRA paper](https://arxiv.org/abs/2305.14314)
Practice: none yet

**25. Progress is the job working, not the bar moving.** A progress bar (epoch 2 of 3) measures completion. Progress is evidence the task is working: validation loss falling, a task score above a baseline, outputs improving. In a long run check in the first percent or so and write an early go or no-go check into the gate, so a setup mistake costs minutes, not days. Watch two curves, training loss and validation loss. Shapes: healthy; plateau; overfitting (validation turns up while training keeps falling); never started (flat from step zero); diverged. Checks that it started: some weight changed, the loss moved, one small batch can be overfit. A flat late loss may only be the learning rate decaying. Loss shows the setup is sound; a task score shows the job works; watch both, on validation data, against a baseline. The same holds for an agent run: activity is how much was done (turns, tool calls, log lines); progress is movement toward the goal, shown by a measure named before the run and recorded in the log at each check. If progress is not recorded, afterward you can only say the run was long and did not finish. A turn budget caps turns; it is not a measure.
Go to: [chapter 9](https://github.com/nikbearbrown/info-7375-prompt-engineering-for-generative-ai/blob/main/chapters/09-training-and-configuration.md), [chapter 4](https://github.com/nikbearbrown/info-7375-prompt-engineering-for-generative-ai/blob/main/chapters/04-the-agent-loop.md), [chapter 11](https://github.com/nikbearbrown/info-7375-prompt-engineering-for-generative-ai/blob/main/chapters/11-tool-use-and-verification.md)
Practice: none yet

**26. Checkpoints.** A checkpoint is a saved snapshot of a run. A full one also holds the optimizer and schedule state, so a run can resume; weights alone are enough to use the model. Use them to recover from a crash or a job time limit, to keep the best (often not the last), to compare, and to branch. Evaluate more often than you save; keep the last two or three plus the best; write the interval and the keep-count in the gate. Compare checkpoints on a fixed panel: the same sample and the same few example outputs each time.
Go to: [chapter 9](https://github.com/nikbearbrown/info-7375-prompt-engineering-for-generative-ai/blob/main/chapters/09-training-and-configuration.md)
Practice: none yet

**27. LoRA, QLoRA and quantization.** LoRA freezes the pretrained weights and trains two small low-rank matrices per chosen layer: far fewer trainable parameters, a small adapter file, and no slowdown at inference once merged. Quantization stores numbers with fewer bits and is lossy. QLoRA is LoRA on a frozen 4-bit base (4-bit NormalFloat, double quantization, paged optimizers); its paper reports fine-tuning a 65-billion-parameter model on one 48 GB GPU while matching 16-bit fine-tuning, where regular 16-bit fine-tuning needs more than 780 GB. How few bits are enough is not settled by theory: measure it with a bit ladder on held-out data, with the tolerance set before you look.
Go to: [the LoRA paper](https://arxiv.org/abs/2106.09685), [the QLoRA paper](https://arxiv.org/abs/2305.14314)
Practice: none yet

**28. Hugging Face and its tools.** The Hub hosts models and datasets. The Python libraries do the training, on any machine, laptop or cluster (PyTorch is installed separately). The `hf` command-line tool does Hub chores such as login, download, upload and launching jobs; it does not train. Hugging Face's MCP server is an agent's interface to the Hub (search, documentation, optional repository and job tools). Spaces host apps and demos, not training; Jobs are paid compute. To read a model listing: the task tag is input to output, then size, base model, licence and the maker's own benchmark claims. Downloads show attention, not quality.
Go to: [the CLI guide](https://huggingface.co/docs/huggingface_hub/guides/cli), [the MCP server docs](https://huggingface.co/docs/hub/agents-mcp), [Jobs](https://huggingface.co/docs/huggingface_hub/guides/jobs), [Spaces GPUs](https://huggingface.co/docs/hub/spaces-gpus)
Practice: none yet

**29. Access tokens.** A token is a password. It never goes in code, a chat with an AI tool, a command line, a batch script or a screenshot. Use the browser login, make a fine-grained token if you need one, one per place you use it, log in only when you publish, and revoke a token at once if it may have leaked.
Go to: [Hugging Face on access tokens](https://huggingface.co/docs/hub/security-tokens)
Practice: none yet

## Part F: Seeing, stopping and owning an agent's work (added 2026-11-09)

**30. Observability and the trace.** The agent sees only its context: the instructions, the task and whatever the program around it puts in, which in some loops includes the results of earlier tool calls. It does not see your folder, your intent or your gate unless something puts it there. You see only the trace you kept: the record of what was requested and what came back. A trace is not the model's reasoning, not its own account ("I saved the file" shows something was said, not that it happened), and not proof that an action worked or was allowed unless the target, the result and the authority were recorded. A check that fails differently, such as listing the folder before and after, is stronger than the agent's report. Exam form: given a situation, say what is observable and what is not.

**31. Provenance.** Provenance is the record of where something came from and who checked it. If there is no way to check what a system did, there is no provenance, and errors hide. A claim without its source, an action without its record, and an approval without what it covered are all provenance gaps.

**32. Stop conditions.** Every run needs its stop conditions written before it starts: each reason the run ends, its status, and who decided it. Poor or inefficient ones cause trouble: no stop at all; a turn budget as the only stop (it stops too late, after the whole budget is spent on repeats, and it caps turns, not time or progress); an over-eager repetition rule that halts useful work; a budget counted in the wrong unit; "finished" read as success; a stop reason nobody recorded. A stop ends the run; it does not show the answer is right. Only a check that a person designed closes the task.
Go to: [chapter 4](https://github.com/nikbearbrown/info-7375-prompt-engineering-for-generative-ai/blob/main/chapters/04-the-agent-loop.md), [chapter 11](https://github.com/nikbearbrown/info-7375-prompt-engineering-for-generative-ai/blob/main/chapters/11-tool-use-and-verification.md)
Practice: none yet

**33. Cost versus risk.** How hard you check should match how bad it is to be wrong. Ask: how cheap is the output to verify, what does being wrong cost, is this an ordinary input or a tail case, can the action be undone, and will it leave a trail? A reversible, low-stakes step can rest on a cheap automatic check; an irreversible or external one needs a human approval. A cheap check that passes does not replace the costly one where the stakes are high. Output is cheap and verification is not, so budget for it.

Claude Code is one. The model only produces text, including a request for a tool call; the harness acts on it. The course's nearest word is host. **36. Fluency trap.** The more fluently an output reads, the more confident you become in it, and then in your own evaluation of it. Form and content are independent: a fluent answer can be wrong, and a green check on a fluent answer shows the shape passed. A fluent sentence establishes nothing.

**38. Prompt versus system prompt.** A prompt is the request for this turn; a system prompt is standing text in the input. Both are requests, not gates: a rule that must hold goes in code between the request and the system, not in a sentence. Revising a system prompt can change behavior a lot while the weights stay the same.

**39. Tools: what they are, and which to use or write.** A tool is an action or an information source that the program around the model makes available; the program decides which are allowed. The model only proposes a tool call (a tool name and arguments); the program checks it, runs it, and returns the result as evidence. When you plan an agent's steps, put tools in the plan: for each step, which tool does it, whether a good one already exists (use it) or must be written, and which operation needs a person's approval. Do not rewrite the wheel *(the instructor's rule, not a sentence in the course text)*: if a well-made tool exists, use it, and write only what does not exist. Each tool you adopt is more to trust and verify, and a tool that exists is not automatically allowed for this task. Exact work (arithmetic, lookups, format checks) belongs in ordinary code or an existing tool, not in the model. Plan errors to spot: a step that needs a capability no tool in the plan provides (the plan is infeasible); a tool with more capability than its step needs; a tool the plan says it will write when a standard one exists; a tool that exists but is forbidden here.

**40. Sandboxes: when to use one.** A sandbox is a contained place where an agent or a tool can act without reaching anything that matters; the course text works with disposable folders, repositories and fixtures and never defines the word. A path check is not a sandbox: it decides whether a proposed target is inside a folder, and it does not contain what the agent can do. A sentence asking the agent to stay in a folder is a request, not a boundary. Put things in a sandbox when the capability is destructive or irreversible, touches what you do not own, or comes from something you have not vetted, and you want to see what it does before it touches anything real *(the instructor's discussion; the rule of thumb is not a sentence in the course text)*. Grant the smallest capability first; a sandbox is the second line. A person still reviews and signs before results move to the real system. Do not claim "sandboxed" without evidence.

**41. Plausibility and the plausibility audit.** Plausibility is whether an output could even be true given what you already know. The plausibility audit is the check you make before you verify: it consults no source, it runs on your own model of how the thing should behave, and it decides whether a source needs consulting and what the verification should look for. Say your verdict, what to look for and why before you look anything up; if you say "I audited it by running the tests," verification has leaked in. Plausibility is a first screen, not evidence, and it fails when: the error is outside your own knowledge (so understand or build the thing yourself first); the output is fluent by construction (a language model produces plausible continuations, so the audit is weakest against the model's own errors); the question has one correct answer (compute or compare it instead); a clean form is mistaken for a trustworthy plan; or the context that decides what is plausible is not in the plan. How deep to audit follows cost versus risk (item 33).

**43. Instruction files: CLAUDE.md and AGENTS.md** *(common usage and the vendor's documentation, checked 2026-11-09; the course text does not discuss these files)*. A coding agent starts every session with a fresh context window, so it does not remember your project. An instruction file is standing text that the program around the model loads into the context at the start of each session: how to work in this project, what to do, what never to do, and which check to run before handing work back. CLAUDE.md is the file Claude Code reads. AGENTS.md is a tool-neutral file that other coding agents read; Claude Code can read it too, or a one-line CLAUDE.md can import it, which is what this course repository does (its CLAUDE.md is the single line `@AGENTS.md`). Why use them: they persist across sessions, they give people and tools one shared set of conventions, and they are the place to write the scope, the constraints and the check (this course's AGENTS.md names `scripts/validate_course.py`). What they are not: a gate. The file is context, a request, and is not enforced; a rule that must hold is enforced outside the model, with a permission rule, a hook, a test or a protected branch. They are also an instruction channel: whoever can edit the file steers the agent, so review changes to it like code. Keep it short and specific, because a long or self-contradicting file is followed less reliably, and remember the agent sees it only if the program loads it.

**44. Verification and validation.** The two words are used with different depths in different sources, so say which you mean. In this course's text, a *validator* checks structure against a contract: required fields, types, allowed values, a path inside the approved folder. That is mechanical, code can do it, and it passes meaningless content that has the right shape (ten meaningless files that were long enough passed a presence check). *Verification* asks whether the substance holds: does the answer follow from the source it cites, did the tool really do the job. It consults something outside the producer (a test run, a reference, a recomputation, a read-back), and a check run by the system that produced the answer is not independent of it. Producing and verifying are different operations (the solve-verify asymmetry): a trustworthy check fails differently from the thing it checks. *Common usage in engineering, not the course text:* verification is "did we build it right, against the specification" and validation is "did we build the right thing, for the real need", so validation is the deeper question, the opposite depth from the course's validator. Either way, passing a validator shows the shape passed; it does not show the claim is true or the need is met. Tool evidence is evidence of something specific: a successful write shows bytes were written, not that the file meets the assignment. Output is cheap and verification is not, so budget for it and match its depth to the risk (item 33).
